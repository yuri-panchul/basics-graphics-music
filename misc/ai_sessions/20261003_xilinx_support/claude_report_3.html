Converged on Vivado

Two independent rewrites of the code that finds a Vivado installation have arrived at the same answer. What is left to compare is not which Vivado they run, but what they tell you and how much code it takes.

codex 9d893916 · 10 commits claude 271f1ccf · 5 commits compared 2026-10-03 against Vivado 2026.1
11 / 11

situations in which both implementations select the identical directory — including an equal-version tie across two vendor directories, a symlinked version directory, and a sort that has been shadowed on PATH.

That is new. Three days ago they disagreed in several cases; each has since adopted the other's better ideas. Both now use shell patterns rather than find, both require a version directory whose name starts with a digit, both hunt for a working version-aware sort instead of trusting the first one on PATH, and both refuse an installation with no version directory at all.

What counts as an installation

Two directory shapes, under a vendor directory named Xilinx, AMD or AMDDesignTools. A candidate counts only if it contains a bin, and only if the directory supplying the version number starts with a digit:

<parent>/<vendor>/Vivado/<version>/bin Vivado 2024.1 and older <parent>/<vendor>/<version>/Vivado/bin Vivado 2024.2 and newer

How an installation is chosen

The same procedure in both. Steps run in order, and the first one that succeeds ends the matter — later steps never run.

  1. 01

    Check the platformcan stop

    Do nothing unless the shell is Linux, Cygwin or MSYS. On macOS and anything else, return at once: Vivado does not run there.

  2. 02

    Obey XILINX_VIVADO if it is setcan stop

    If that variable names a directory that has a bin inside, put the bin on PATH and stop. Nothing is searched. This is how you pin one specific version, or point at an installation in an unusual place.

    If it is set but there is no bin there, warn and carry on rather than fail.

  3. 03

    Leave a working vivado alonecan stop

    If vivado already runs from PATH — because you sourced settings64.sh yourself — change nothing and stop.

  4. 04

    Decide where to look

    In order: XILINX_HOME first if it is set, then the standard parents for the platform — $HOME, /opt, /tools on Linux, or /c, /d, /e on Cygwin and MSYS.

  5. 05

    Collect what one place has to offer

    Within a single parent directory, try all three vendor names and both directory shapes. Keep every match that has a bin and whose version directory starts with a digit, remembering the version number alongside the path. The digit rule is what keeps the installer's own DocNav, xic and .xinstall directories out of the running.

  6. 06

    Nothing here? Move on. Something here? Stop looking.

    A parent with no candidates is skipped, and if it was the one you named in XILINX_HOME, you are told. The first parent that does yield candidates ends the search — later parents are never examined. That is what makes XILINX_HOME authoritative and lets $HOME win over /opt.

    only claude says anything here

    If a skipped directory looked like an installation but its name did not start with a digit, claude names it in a warning and suggests XILINX_VIVADO. Codex skips it without comment.

  7. 07

    Find a sort that can really compare versions

    Try /usr/bin/sort, then /bin/sort, then whatever sort is on PATH, and accept one only after watching it put 2026.2 before 2026.10. Checking that the -V option is merely accepted is not enough. The reason for the search is Cygwin and MSYS, where the sort on PATH can be the sort.exe of Microsoft Windows.

    If none of the three qualifies, fall back to plain sort and warn that an older version may be picked.

  8. 08

    Pick the newest version from that one place

    Every candidate from that parent competes, whatever its vendor directory or layout, compared on the version field alone so a path can never sway the result. Carriage returns are stripped first, in case the sort came from Windows. If there was more than one candidate, a warning lists them and names the winner.

    tie-breaking

    Codex adds -k2,2, so two installations of the same version are resolved by path, deliberately and documented. Claude leaves it to the sort's own last-resort comparison, which happens to give the same answer.

  9. 09

    Publish the resultstops

    Set XILINX_VIVADO to the winning directory and append its bin to PATH.

  10. 10

    If every place came up empty, fail with instructionsstops

    The error names the parents that were tried, the three vendor directory names, both expected layouts, and the two environment variables that override the search.

The two implementations

xilinx_codex

284 lines · 3 functions

Advantages

  • Much smaller for the same behaviour — 284 lines against 403, and three functions against six. Easier to hold in your head.
  • Leaks nothing into your shell. Every working variable is local; this file is sourced, not executed.
  • Quotes each path individually in the multiple-installation warning, so a path containing a space stays readable.
  • Tie-breaking is explicit and documented (-k2,2) rather than left to the sort's last-resort behaviour.
  • Candidate collection is a pure function that prints records to standard output, so it can be exercised on its own without the rest of the machinery.
  • Also contributes the style rules it follows, extending AGENTS.md with the Bash spacing conventions.

Disadvantages

  • Says nothing about a directory it skips. A real installation under a directory named build or v2024.1 disappears from the search in silence.
  • Three new lines past 79 columns, where the file's own convention is to stay inside it.
  • Keeps an unreachable branch — the else error "this script does not support your OS" cannot be reached, because the function already returned for any other platform.
  • The two layouts are described in the error text separately from the patterns that implement them, so the two can drift.

xilinx_claude

403 lines · 6 functions

Advantages

  • The only one that explains a skipped directory, naming it and suggesting the variable that would override the rule.
  • No new line past 79 columns — the three in the file are untouched upstream lines.
  • No dead code — the unreachable platform branch is gone.
  • One documented constant for the vendor list, read by the loops and by every message, so the code and its diagnostics cannot disagree.
  • Warning text names the concrete risk — that 2026.9 would be taken for newer than 2026.10 — rather than describing it abstractly.

Disadvantages

  • 42% more code for the same selection, spread over twice as many functions. The extra buys one warning and shorter source lines.
  • Joins paths with spaces inside a single pair of quotes in the multiple-installation warning, which is ambiguous if a path contains a space.
  • One variable still leaks — xilinx_vendor_dirs, kept at file scope on purpose as the configuration knob, but a leak all the same.
  • The xilinx_append_to helper is clever rather than plain, using printf -v and indirect expansion to keep the accumulator lines short.
  • Two comment blocks do not follow the spacing exception codex's branch adds to AGENTS.md; if that document is merged, this file no longer conforms to it.
  • The sort-failure error path is untested. It is reachable only if a sort that passed the probe later fails, which I could not construct.

Recommendation

Merge codex, then carry over one warning.

When two implementations pick the same directory in every situation, size and clarity decide, and codex is 119 lines smaller with half the functions and no leaked variables. The one thing it lacks that matters is the message naming a directory it skipped — the difference between a student seeing why their install was ignored and seeing nothing.

  1. Take xilinx_codex as the base, AGENTS.md spacing rules included.
  2. Port claude's skipped-directory warning into xilinx_collect_vivado_candidates, or alongside it.
  3. Reflow codex's three long lines to stay inside 79 columns.
  4. Delete codex's unreachable else error "unsupported OS" branch, or move the platform list into one variable so the branch becomes reachable and meaningful.
  5. Adopt claude's wording for the no-version-sort warning, which names 2026.9 against 2026.10.

Point 4 is a genuine choice rather than a port: codex restored that branch deliberately on a6e378bf. Dead code that documents an intention is still dead code, but if the platform list is ever extended, that branch is what catches the omission.
