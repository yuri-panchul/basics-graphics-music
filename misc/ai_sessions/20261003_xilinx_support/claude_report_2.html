Choosing Vivado

How the course scripts decide which Vivado installation to run, written out step by step — and how the two rewrites of that decision, on xilinx_codex and xilinx_claude, differ. They now agree in eight of nine tested situations.

codex 6f5c569c · 6 commits claude a38fb114 · 4 commits compared 2026-10-03 verified against Vivado 2026.1

What counts as an installation

Both versions look for two directory shapes, under a vendor directory named Xilinx, AMD or AMDDesignTools. A candidate only counts if it contains a bin subdirectory:

<parent>/<vendor>/Vivado/<version>/bin Vivado 2024.1 and older <parent>/<vendor>/<version>/Vivado/bin Vivado 2024.2 and newer

An installation with no version directory at all — plain /opt/Xilinx/Vivado/bin — is deliberately not recognised by either version any more. Both briefly supported it and both removed it, on 6f5c569c and a38fb114 respectively.

How an installation is chosen

The same procedure in both versions. Steps run in order and the first one that succeeds wins — later steps never run.

  1. 01

    Check the platformmay exit

    Do nothing at all unless the shell is Linux, Cygwin or MSYS. On macOS and anything else the function returns immediately, because Vivado does not run there.

  2. 02

    Obey XILINX_VIVADO if it is setmay exit

    If you have pointed XILINX_VIVADO at a directory and that directory has a bin inside it, add that bin to PATH and stop. Nothing is searched. This is the escape hatch for an installation in an unusual place, or for pinning one specific version.

    If the variable is set but there is no bin there, warn and carry on to the next step rather than fail.

  3. 03

    Leave an already-working vivado alonemay exit

    If vivado can already be run from PATH — because you sourced settings64.sh yourself, say — change nothing and stop.

  4. 04

    Build the list of places to look

    In order: XILINX_HOME first if it is set, then the standard parents for the platform — $HOME, /opt, /tools on Linux, or /c, /d, /e on Cygwin and MSYS.

  5. 05

    Take each place in turn and collect candidates

    Within one parent directory, try all three vendor names and both directory shapes, and keep every match that has a bin. The directory that supplies the version number is remembered along with the path.

    xilinx_claude only

    The version directory must also start with a digit (-name '[0-9]*'). This is what keeps the installer's DocNav, xic and .xinstall siblings out of the candidate list.

  6. 06

    If that place had nothing, move on — otherwise stop looking

    A parent directory with no candidates is skipped, and if it was the one you named in XILINX_HOME you get a warning saying so. The first parent that does yield candidates ends the search: later parents are never examined. That is what makes XILINX_HOME authoritative, and $HOME win over /opt.

  7. 07

    Pick the newest version among that place's candidates

    All candidates from that one parent compete regardless of vendor directory or layout, compared by version number rather than as text, so 2026.10 correctly beats 2026.9. If there was more than one candidate, a warning lists them all and names the winner.

    xilinx_codex

    Hunts for a working version-aware sort: it tries /usr/bin/sort, /bin/sort, then sort, and checks each one actually orders 2026.2 before 2026.10 before trusting it.

    xilinx_claude

    Asks only whether sort accepts the -V option, and uses whichever sort is first on PATH.

  8. 08

    Publish the resultexit

    Set XILINX_VIVADO to the winning directory and append its bin to PATH.

  9. 09

    If every place came up empty, fail with instructionsexit

    The error names the parent directories that were tried, the three vendor directory names, both expected layouts, and the two environment variables that can override the search.

Where the two differ

I sourced both files from one harness under set -Eeuo pipefail against identical fake installation trees. Eight of nine cases select the same directory; one does not.

A tenth case is not about the trees but about the environment, and it separates them too:

A sort that rejects -V is first on PATH 
$ PATH=$H/fakebin:/usr/bin:/bin   XILINX_HOME=$H/new    # holds 2026.9 and 2026.10

codex   XILINX_VIVADO=…/new/AMD/2026.10/Vivado      ← falls back to /usr/bin/sort
claude  XILINX_VIVADO=…/new/AMD/2026.9/Vivado       ← warns, then picks the older one

This is the Windows case: under MSYS and Cygwin a Microsoft sort.exe can sit ahead of GNU sort on PATH. The repository already works around the same hazard for find, via the $find_to_run variable in 00_setup.source_bash.

The two implementations

xilinx_codex

241 lines · 6f5c569c

Advantages

  • Survives a shadowed sort, by searching for a working one and functionally testing it on 2026.2 against 2026.10 rather than trusting that -V was accepted.
  • Sorts on the version field alone (-t $'\t' -k1,1V), so a path can never influence a version comparison.
  • Strips carriage returns from sort output, for Windows tools.
  • Leaks nothing. Every working variable is local; these files are sourced into your interactive shell, not executed.
  • No dependency on find — plain shell globs, which sidesteps the find.exe problem entirely.
  • Accepts an unusual version directory name, so a hand-built or renamed tree still works.
  • Flattest control flow: one loop over parents with an early return, so no accumulation across parents and no guard needed to keep XILINX_HOME authoritative.
  • Smallest of the three revisions, at 241 lines against upstream's 255.

Disadvantages

  • The vendor list is written out three times — two loops and the error message — so the search and its own documentation can drift apart.
  • Nothing filters installer siblings by name. DocNav and xic are excluded only because they happen to have no bin; a future installer directory that does have one would be offered as a version.
  • A multi-line string is passed to a single-line warning helper. warning does info warning: $* unquoted, so word splitting mangles the tabs and newlines of the candidate list.
  • Capitalised messages (Cannot find Vivado under:) break this file's own convention; every upstream message here starts lowercase.
  • Dead code: return 1 after error, twice — error already exits.
  • Unquoted paths in the final error (${search_parents[*]}), ambiguous if any path contains a space.

xilinx_claude

330 lines · a38fb114

Advantages

  • One source of truth for the vendor list. xilinx_vendor_dirs drives both loops and the text of every message, so they cannot disagree.
  • Excludes installer siblings by name, not by luck: the [0-9]* match keeps DocNav, xic and .xinstall out whatever they contain.
  • Both layouts documented in one header comment instead of as remarks scattered through the loops.
  • Readable diagnostics: a single-line warning that lists every candidate and names the one chosen.
  • Follows local convention — lowercase messages, and the same ..._try_install_dir helper shape the Quartus setup script already uses.
  • Quotes every path it prints in a diagnostic.

Disadvantages

  • Picks the wrong version when sort is shadowed, with only a warning to show for it. The one case where a user ends up running software they did not choose.
  • The sort probe tests the wrong thing — that -V is accepted, not that it works.
  • Silently ignores a version directory that is not a number, falling through to another parent without saying why.
  • Leaks 10 variables into the sourced shell, including vivado_candidates and chosen_vivado_dir.
  • 132-column lines, 7 of them past 79 — the only revision that breaks the file's established formatting.
  • 37% more code than codex for behaviour that differs in one case, and keeps an unreachable else error "unsupported OS" branch.

Recommendation

Base on xilinx_codex; port the presentation from xilinx_claude.

The codex advantages are about getting the right answer in a hostile environment, and one of them — the shadowed sort — changes which Vivado a student actually runs. The claude advantages are about how the code and its messages read. Presentation is cheap to port in either direction; the sort handling is not.

Six edits to carry across:

  1. Hoist the vendor list into one variable used by both loops and every message.
  2. Add the [0-9]* name filter, so installer siblings are excluded by rule rather than by having no bin.
  3. Add the header comment describing both layouts in one place.
  4. Collapse the multiple-installation warning onto one line that names the winner.
  5. Lowercase the message text to match the rest of the file, and quote the paths in the final error.
  6. Delete the two return 1 statements that follow error.

Edit 2 is the one real disagreement rather than a port: it trades codex's tolerance of an odd version directory name for certainty about the installer's own sibling directories. Worth taking, since the siblings ship with every install and an odd version name is something you would create deliberately — and XILINX_VIVADO already covers that case.

Both branches exercised against a real Vivado 2026.1 install at /home/verilog/AMD/2026.1/Vivado on Simply Linux 10.4, glibc 2.32.
