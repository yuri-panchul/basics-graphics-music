I am not a Bash scripting virtuozo but I can evaluate the quality of Bash code.

That was enough to try an experiment: give Claude and Codex separate clones of the same repository, let each develop a solution, and then ask each to examine the other’s work. I would read their arguments, ask about concrete failures, and decide which recommendations to adopt. The subject was a small but consequential piece of infrastructure: the Bash script that finds a Xilinx or AMD Vivado installation.

The repository is basics-graphics-music, or BGM, a collection of portable Verilog and SystemVerilog examples for learning FPGA and ASIC design. It gives educators a common starting point for laboratory exercises, with scripts for selecting a board, running the tools, and putting a design onto hardware. Students can spend their attention on the circuit they are building.

This becomes particularly useful when you have a zoo of boards. A classroom may contain older Terasic boards with Altera FPGAs, Digilent boards with Xilinx devices, and inexpensive Gowin boards from Sipeed. BGM’s board support accommodates that variety. Its board wrappers and tool scripts handle differences around the lab design. Portability still takes work, but each instructor does not have to reconstruct the entire environment for every board.

These are teaching materials with a travel history. The repository records use at Hacker Dojo in Mountain View, United States; ADA University in Baku, Azerbaijan; LaLambda in Tbilisi, Georgia; and the AUCA and Siemens EDA seminar in Bishkek, Kyrgyzstan. The event list gives the locations and dates. At the ADA University seminar, the exercises progressed from basic logic through graphics and sound to a small RISC-V CPU. A reliable setup script helps make that progression possible on the equipment a particular institution has.

The change I needed was easy to describe. The Vivado setup script, scripts/steps/00_setup_xilinx.source_bash, had to understand both directory layouts below, with Xilinx, AMD, or AMDDesignTools as the vendor directory:

<parent>/<vendor>/Vivado/<version>/bin
<parent>/<vendor>/<version>/Vivado/bin

It also had to choose versions sensibly. An installation named 2026.10 should beat 2026.2 when both compete in the same search location. Paths might contain spaces. A version directory might be a symbolic link. On a Windows machine running a Bash environment, the command named sort might be Microsoft’s utility rather than the Unix program the script expected. The second Codex report lays out these cases and the selection policy.

I kept the implementations in ~/codex and ~/claude, on the branches xilinx_codex and xilinx_claude. Separate clones made the comparison tangible: each assistant had actual files to inspect, and each could change its own implementation without overwriting the other’s work. I could inspect a diff, keep a commit, or ask for another revision.

The first useful result was that the implementations had different strengths. Codex’s first comparison found its own version stronger at locating a suitable Unix sort and recognizing symlinked installations. It also found an embarrassing counterexample: a directory named backup, containing a bin subdirectory, could be selected as the newest version. Claude’s digit-prefix filter excluded it. That is a much more useful criticism than a general statement that one implementation is cleaner.

Claude’s first review recommended using Codex as the base while carrying over improvements from Claude. It called out the repeated vendor list, awkward candidate messages, and redundant returns after an error helper that already exits. Here was one assistant recommending the other assistant’s implementation, while still identifying worthwhile changes to it. I did not have to choose an entire package of strengths and weaknesses.

The review cycle then became quite practical. I asked for another comparison, read the advantages and disadvantages, and told the assistant to adopt the useful recommendations. Codex acquired a centralized vendor list, a separate candidate-collection function, and the numeric-name filter. These are concrete changes advocated in Claude’s second report. Filtering names is a policy choice: it rejects renamed installations such as mybuild, but an explicit installation variable provides an escape hatch. I could evaluate that tradeoff against the installations we intended to support.

In the other direction, the later Claude implementation adopted shell globbing, the search for Unix sort in known locations, a test of actual version ordering, and cleanup of Windows carriage returns. Claude’s third report describes this convergence. The two implementations increasingly expressed the same requirements, even though their function structure and diagnostics remained different.

The sort example captures why I liked this process. It is tempting to ask whether a command accepts -V and call the problem solved. A stronger check gives the command two deliberately troublesome versions and examines the result. Codex also tried /usr/bin/sort and /bin/sort before trusting sort on PATH. If no suitable implementation was available, the requested fallback was plain sorting with an explicit warning that it might choose an older release. The second comparison’s tests made the consequences visible.

I also changed the scope. We briefly supported automatic discovery of installations without version directories, such as /opt/Xilinx/Vivado/bin. I later asked both sides to remove that special case and assume versioned installations for discovery. That decision simplified the problem. The assistants could propose compatibility features; I still had to decide which ones belonged in the repository.

Readability received the same attention. I asked for comments explaining the less obvious Bash substitutions, including operations equivalent to basename. I specified where blank lines should go, how multiline diagnostics should be separated from following commands, and how continuation backslashes should align. The conventions went into AGENTS.md and CLAUDE.md. In teaching infrastructure, code that another contributor can understand next month has practical value.

The most useful question became: “Which concrete case proves that this change is better?”

That question applies to the reviews themselves. Claude’s third report recorded agreement in eleven selection scenarios and recommended the smaller Codex implementation as the base. That supported convergence on the search policy. It did not establish that every failure path was equivalent. Its test matrix needs to be read alongside the other reviewer’s evidence.

Codex’s third report tested a failing sort probe under set -Eeuo pipefail. Claude’s unguarded assignment could terminate setup before trying the next sort program; Codex’s conditional probe continued. It also tested an apostrophe in a directory name: Claude’s xargs-based diagnostic could fail after a valid installation had already been selected. The lesson was specific. Probe failures need deliberate handling, and formatting an informational message should not reinterpret the user’s pathname.

The same report explains the limits of those tests: Windows behavior was simulated, and its comparison did not run native Windows or end-to-end synthesis. I would preserve that distinction when describing the result. Agreement between two reviewers is useful evidence, and their test coverage still has boundaries.

The solution we converged toward can be explained without reading Bash. Respect a valid explicit XILINX_VIVADO directory; otherwise keep an existing vivado command on PATH. If discovery is needed, search XILINX_HOME first, then the platform defaults. Linux uses $HOME, /opt, and /tools; Cygwin/MSYS uses /c, /d, and /e, corresponding to Windows drives C:\, D:\, and E:\. Within the first parent that has candidates, compare versions across both layouts and all three vendor names. This gives location priority over a newer installation somewhere else.

The retained implementation uses a digit-prefix filter, preserves symlink support, tests sorting behavior, makes equal-version ties deterministic, and formats paths without xargs. It sets XILINX_VIVADO and appends the selected bin directory to PATH. That last detail is worth understanding: an earlier executable on PATH can still win. Nor does finding a bin directory validate the executable or its license. The Codex script after the review and readability changes is the concrete result, with these limits intact.

I would use this method again for work I can review but do not want to write entirely from scratch. Start with separate working copies, ask each assistant to assess both implementations, and require examples for important claims. Then give the useful criticism back to the other side and repeat. Keep the human decisions visible: supported cases, acceptable fallback behavior, code style, and what evidence is sufficient to accept a change.

The outcome was a Bash implementation assembled from ideas that survived comparison. Claude contributed useful structure and filtering; Codex contributed stronger handling of awkward environments and paths; my part was to set the requirements and judge the tradeoffs. For BGM, the payoff is concrete: a student selects a board, the scripts locate the tools, and the seminar can move on to the logic, graphics, music, or processor the student came to build.
