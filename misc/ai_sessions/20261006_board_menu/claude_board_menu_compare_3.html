One difference left

I took the one thing the last comparison said codex got right: the two-size boards are now listed by name, not matched by a numeric suffix. The two base-name functions now agree on every name I can invent. What remains between the implementations is a single structural choice about sort.

What changed on my side

Commit 598a51b2 replaces fpga_board_size_suffixes with fpga_board_families, which names the four directories instead of stripping _35, _50 and _100 from anything that ends that way.

- fpga_board_size_suffixes="
-     _35
-     _50
-     _100
- "
+ fpga_board_families="
+     nexys_a7_50:nexys_a7
+     nexys_a7_100:nexys_a7
+     arty_a7_35:arty_a7
+     arty_a7_100:arty_a7
+ "

The recursion that removes suffixes is now fpga_board_base_search, and fpga_board_base is a thin wrapper that applies the family mapping once the search has finished. Applying it inside the recursion would have let it change which way an overlapping suffix is split; applying it to the finished name cannot.

No current board changes group. 55 tests pass, including two new ones that exist precisely to pin the behaviour I was getting wrong.

The one difference that remains

claude

no external command in the menu path

fpga_board_sort is an insertion sort in Bash with local LC_ALL=C. 52 names cost about a millisecond, which measured less than starting sort at all: 14 ms against 18 ms for ten menu builds.

Nothing to probe, nothing to fall back to, no new way for the setup to fail, and the order is the same under every locale because the comparison is by byte value.

codex

an external sort, discovered

fpga_board_sort_discovery probes /usr/bin/sort, /bin/sort and then sort from PATH with a sample only a C-ordering sort gets right, so a Windows sort.exe first on PATH cannot win.

If none qualifies it reports no Unix-compatible sort and returns failure, which stops the board selection. Their own test pins that path, so it is a deliberate fail-closed choice rather than an oversight.

I prefer mine, but the honest summary is that this is a judgement call about dependencies, not a correctness difference. Theirs fails loudly in an environment that would otherwise sort wrongly; mine has no such environment to worry about. Their discovery test is the better piece of craft either way: it shadows /usr/bin/sort with a Bash function of that name to simulate all four outcomes without touching the filesystem, and separately puts a fake sort first on PATH to prove it is not used.

What this exercise actually produced

Three rounds of comparison moved four things that neither of us would have found alone.

  1. The leading-zero bug was mine, found by codex, and the worst case was not the crash but the silent one: with a selection file present, 08 left the old board in place with fpga_toolchain=none and exited 0.
  2. The xargs -L 1 bug was pre-existing, found by codex because their test forces the Darwin branch on Linux. Under GNU findutils the board list became 113 copies of %.
  3. The menu walk was mine, taken by codex: explore the menu with numbers only and assert every directory is reachable exactly once, so the test cannot agree with a wrong grouping.
  4. The sorted first level was mine, taken by codex, and the family table was theirs, taken by me.

The remaining difference is a dependency judgement, which is a reasonable place for two implementations to disagree.
