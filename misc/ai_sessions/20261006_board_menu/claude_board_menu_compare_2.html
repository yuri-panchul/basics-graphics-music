The menus are now the same menu

Both implementations took the same sixteen points of feedback and split the work into the same four commits. The result is a menu that is identical item for item, and identical on every input I could think to type. What is left to compare is the machinery behind it — and there one of us made the safer choice.

Verdict

No behavioural difference remains in the menu itself. The first level is identical — 52 boards plus exit, same labels, same stars, same order. The second levels match. Fourteen different inputs, including every leading-zero case and both letter shortcuts, select the same board in both.

Codex made the better call on the size suffixes. I added _35, _50 and _100 to a generic list; codex wrote a two-line case naming the four directories. Mine would silently fold a future new_board_100 into new_board. Theirs would not. I should take their version.

I removed the dependency they kept. Codex discovers an external sort and fails the whole setup if it cannot find one with C ordering. I sort 52 names in Bash, which measured faster than starting sort at all, so there is nothing to discover and nothing to fail.

The one place the designs really differ

You asked for nexys_a7_50 and nexys_a7_100 to be configurations of nexys_a7, and likewise for Arty. We implemented that in opposite ways.

claude

a generic list of size suffixes

fpga_board_size_suffixes="
    _35
    _50
    _100
"

Treated like any other suffix by the same search, with a comment warning not to grow the list casually.

codex

an explicit case on four names

case "$base" in
    nexys_a7_50 | nexys_a7_100 ) base=nexys_a7 ;;
    arty_a7_35  | arty_a7_100  ) base=arty_a7  ;;
esac

Applied after the suffix search, affecting only the four directories that exist.

On every directory in the repository today the two agree. They part company on names that do not exist yet, which is exactly where a rule of this kind earns or loses its keep:

Sorting: a dependency, or none

Your point nine was that sort -u may be missing on Windows. We answered it differently.

Codex kept the external sort and wrote a discovery for it, modelled on xilinx_sort_discovery: probe /usr/bin/sort, /bin/sort, then sort from PATH, with a sample that only a C-ordering sort gets right. If none qualifies, it reports and returns failure — and the board selection stops. Their own test pins that path:

from codex's test, the fourth case
"no_compatible_sort": … expected None
    self.assertIn("NO_SORT", result.stdout)
    self.assertIn("no Unix-compatible sort", result.stderr)

I measured whether the dependency was worth keeping, and it was not:

pure bash insertion sort   : 14 ms for 10 x 52 names
LC_ALL=C sort -u in a pipe : 18 ms for 10 x 52 names

Sorting 52 strings in Bash is cheaper than starting the process that would sort them, so fpga_board_sort does it in the shell with local LC_ALL=C. There is no probe, no fallback, no new failure mode, and nothing to explain in the README beyond one sentence. That part I would keep over theirs.

Their discovery test is still worth admiring for its trick: it shadows /usr/bin/sort with a Bash function of that name, so all four discovery outcomes can be simulated without touching the filesystem. They also test that a fake Windows sort placed first on PATH is not used. I have no equivalent because I have nothing to discover, but the technique generalises.

What each side borrowed from the first report

Both of us acted on the previous comparison, which makes this round a reasonable test of whether that exercise was worth anything.

claude took from codex

  • The sandbox harness: a throwaway repository with stub toolchain modules, running the real script in 0.12 s instead of 2.4 s. My suite now checks the bytes of the selection file, the chosen toolchain, the saved-selection bypass, the hackathon override and all four OSTYPE branches.
  • The --baseline replay of all 110 boards through the old flat menu.
  • A catalogue check derived from boards/README.csv, so a grouping bug cannot hide behind a suffix-based expectation.
  • Returning a status on cancellation instead of calling exit, and local PS3 REPLY.
  • Full directory names on the second level.
  • Their xargs -L 1 diagnosis, applied once you confirmed it could go.

codex took from claude

  • The menu walk: test_walk_menu_reaches_only_eligible_configurations_once is the test I argued for — explore the menu with numbers, assert every directory is reachable exactly once, do not compute the grouping.
  • Sorting the first level by board name, which is what fixed their de0_nano_soc ordering.
  • An explicit message when no board directories are found.
  • A test that the helper's cancellation preserves prompt state.

The bug that started this round, for the record

Codex's first report found it and I confirmed every part: the menu read the answer with $(( REPLY - 1 )), so 010 selected item eight and 08 aborted. The worst case was not the crash but what followed it — with a selection file already present the script printed value too great for base, then exited 0 with the previously saved board and fpga_toolchain=none.

It was the direct cost of a decision I had presented as an advantage in my own first report: choosing items by number rather than by label text. Codex was immune because they use the label select hands back. Both designs avoid one class of bug and have to handle the other — mine now normalises the answer explicitly, theirs now reverses two display strings back into values, for the star marker and for the alias label. Neither is wrong; both are places to be careful.

What I will change

  1. Replace my size-suffix list with codex's case. Four names explicitly, no generic numeric stripping, so a future new_board_100 cannot be folded into new_board. One commit, and the existing tests should pass unchanged except for the two synthetic cases, which become the proof that it is fixed.
  2. Add their PATH-shadowing test technique where I have an external command worth pinning. I have none in the menu now, but the Quartus and Vivado discovery code does.
  3. Merge main, which now carries e8b9de12, your fix for the three 50 MHz include paths.

What I would not change: the pure-Bash sort, which removes a dependency rather than discovering one, and the 53-test suite, which is twice the size of theirs and earns it on the walk, the synthetic board lists and the mutation-tested suffix logic.

If the two were merged

Take codex's explicit case for the sizes and their PATH-shadowing test trick; take my pure-Bash sort and my test suite; everything else is already the same code written twice. The menu needs no reconciliation at all — it is the same menu.
