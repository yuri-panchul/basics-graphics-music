How each implementation chooses a configuration

The shared surrounding setup gives a hackathon-file override priority. It otherwise reuses a valid saved selection when no new choice is requested. These steps describe the path when a menu is needed.

Codex, in plain English

  1. Find a sorter that actually produces the required C ordering, preferring the Unix tools at /usr/bin/sort and /bin/sort before trying PATH.
  2. List board directories, leaving out the retired container. Sort their names using the verified program with LC_ALL=C.
  3. Skip hackathon names while building menu candidates. Remove recognized trailing configuration endings with one regex. Then apply explicit Nexys A7 and Arty A7 family mappings.
  4. Collect unique board/family names, sort those names, and mark each group having multiple visible configurations with *.
  5. Use Bash’s selected label. Remove the first-level display marker; choose a singleton immediately or show the group’s full configuration names.
  6. Remove the known legacy-alias annotation from the selected display value when needed. Save the original configuration name and use its existing toolchain dispatch. The generated file lists only the 110 interactive choices.

Claude, in plain English

  1. List all board directories and pass them through LC_ALL=C sort, using whichever sort PATH resolves.
  2. Remove the retired container from the discovered list. Skip hackathon names when constructing the menu.
  3. Recursively try known configuration endings and the numeric endings _35, _50, _100. Keep the shortest nonempty remainder as the group name.
  4. Deduplicate those names and sort them with a Bash insertion-sort helper using local LC_ALL=C. Count configurations and add the same * markers.
  5. Normalize a valid numeric answer as decimal and use it to look up the original name in a separate array. Show full configuration names; obtain alias annotations from a small alias table.
  6. Save the original selected name and use the same toolchain dispatch. The generated file includes 110 interactive choices plus two commented hackathon configurations.

On the current board set and a compatible Unix sort, the observable menu labels and numeric selection paths agree, despite these different algorithms.

Verified findings and their impact

Priority 1 · Claude Directory discovery still trusts PATH’s sort

Claude’s Bash sorter protects the derived first-level names. It does not protect the initial directory list: both platform branches still invoke bare sort from PATH. Configuration order within each family comes from that initial list. Consequently, a foreign or failing PATH sorter can stop setup or change variant numbers even though the first menu is sorted correctly.

The review injected a temporary sort executable at the front of PATH while retaining the real Unix sorter at /usr/bin/sort. Two full-setup probes produced:

Exits with status 1Uses its verified absolute-path sorter; selection succeeds.Setup exits with status 1 before the menu.
Outputs names in reverse orderNormal variant order; 33 → 1 saves nexys_a7.First-level order remains correct, but variants are reversed; 33 → 1 saves nexys_a7_50.

This is a reproduced numbering-stability problem, not the old bug where the displayed item and selected value disagreed. With reverse sorting, Claude displays nexys_a7_50 as item 1 and selects it correctly. The same classroom instruction or scripted pair of numbers now means a different configuration.

Recommendation: adopt Codex’s sorter discovery for the initial scan, or extend the Bash sorter to the discovered directory list too. An internal sorter can remove the external dependency only if every relevant stage uses it. These are simulated incompatibility tests on Linux, not a native Windows-sort execution. With a closed input stream at the second menu, Codex returns cancellation immediately. Claude prints the first menu again before its next read returns EOF. Both preserve the saved selection. Direct cancellation probes also confirmed that both restore preexisting PS3, REPLY and locale values.

Claude still says “amoung” in its first prompt and uses “Your choice” at both levels; Codex’s prompts explicitly say “Board” and “Variant” and advertise uppercase shortcuts too. These are minor readability differences.

Advantages and disadvantages of each implementation

Codex advantages

  • Verified sorting across both stages. Directory and board-name sorting share the discovered C-compatible executable.
  • Limited family rules. Only known Nexys A7 and Arty A7 names are grouped by chip variant; unfamiliar numeric endings remain intact.
  • Smaller setup patch. A single suffix-sequence regex, direct use of Bash’s selected values, and shorter menu control flow reduce bookkeeping.
  • Default full-setup coverage. The standard suite checks every eligible configuration’s exact saved file and expected toolchain, plus sorter failures, locale variation, aliases, markers and cancellation.
  • Clear helper behavior. EOF and an empty menu return control, while prompt state stays local.

Codex disadvantages

  • Requires a compatible external sorter. It reports a missing dependency if none passes its probe; no built-in fallback is provided.
  • One command substitution per configuration. Base-name calculation forks and reconstructs the suffix array/pattern each time. The regex is concise but needs careful explanation.
  • Alias presentation is special-cased. Adding more aliases means keeping label creation and label-to-name conversion consistent. Claude’s separate name array/table is more extensible.
  • Some input tests are narrower. The shipped suite tests leading zeros but could add Claude’s whitespace, plus-sign and zero-padded control-item cases. Independent probes confirmed the tested plus/space inputs already work.
  • Exact display identifiers still matter to dispatch. Codex removes the star and known alias text from selected labels. This is small for the present menu, but richer annotations would favor explicit label/name separation.

Claude advantages

  • Extensible metadata. Separate alias and non-board tables make those policies visible and easy to extend.
  • Display labels are separate from values. Decimal indices retrieve original names without undoing presentation annotations.
  • Fewer per-board subprocesses. Base-name recursion returns through a result variable; first-level sorting is performed in Bash.
  • Broader input-focused tests. The suite covers spaces, plus signs, padded controls, shortcut prompts and hypothetical input lists.
  • Integration testing has improved substantially. It now includes the temporary-repository harness, saved files, toolchain checks, hackathon overrides, platform branches and an optional old-menu comparison.

Claude disadvantages

  • Incomplete protection from PATH sort. The independent first-level sorter does not cover discovery or variant ordering.
  • Global numeric stripping is too general. It combines future numbered names without a family-specific rule.
  • More moving parts. Recursion, pair strings, several parallel arrays, explicit decimal parsing and global result variables increase the code to review.
  • Default exhaustive integration coverage is weaker. The standard run walks every menu choice, but full old-versus-new comparison requires --baseline. Its default integration tests cover selected examples; they do not check all files/toolchains as Codex’s default test does.
  • Small cleanup opportunities remain. Second-level EOF redisplays the first menu, the empty-list error exits the caller, and one prompt retains a typo.

The algorithms have different costs: Codex starts a subshell for each base; Claude explores overlapping suffix paths recursively, scans pairs for group counts and uses insertion sort. No performance winner is claimed here. Suite runtimes include different tests and concurrent machine load, and are not menu-startup benchmarks.

What each side can adopt next

Codex can adopt from Claude

  1. The additional numeric-input cases: leading/trailing spaces, +8, and zero-padded Back/Exit, as regression tests rather than new parsing code.
  2. A small alias table and separate stored values if more legacy aliases or annotations are introduced. There is no need to enlarge the current code solely for hypothetical reserved board names.
  3. The Bash sorting idea as an optional fallback if supporting systems with no compatible Unix sorter becomes a requirement. Test byte ordering and apply any fallback consistently to directories and groups.
  4. More isolated helper tests with synthetic inventories when those tests add negative cases beyond the existing full-setup suite.

Claude can adopt from Codex

  1. Fix discovery sorting first. Use a behavior-tested sorter in every external sorting call, or replace the remaining call with the internal sorter. Add the failing/reverse-PATH probes from this review.
  2. Use explicit Nexys A7 and Arty A7 family rules. Preserve unrelated _35/_50/_100 names and test that boundary independently of the implementation’s suffix list.
  3. Check every configuration’s saved output and toolchain by default. Keep the optional baseline test, but make core exhaustive integration checks part of a normal test run.
  4. Consider the regex implementation to simplify the suffix algorithm, and direct EOF return to simplify cancellation. Preserve the now-correct decimal handling if retaining index-based selection.
Recommended direction: keep the converged menu design. Prioritize complete sort protection and family-specific numeric grouping; use the two test suites’ complementary cases. Alias tables and a built-in sorting fallback are maintainability options, not prerequisites for the current 110 configurations.
