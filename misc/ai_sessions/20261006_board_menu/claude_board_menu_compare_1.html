Two menus, one partition

Claude and Codex were given the same task on separate clones: turn the 113-entry flat board menu into two levels. Both branched from 77959f67. They arrived at the same 56 boards by different algorithms — and one of them picked up a macOS bug on the way.

Verdict

The groupings are identical. 113 board directories, 56 boards, same partition, verified name by name. The only divergence is the label of four single-configuration boards. Every board remains selectable in both, so both satisfy the equivalence requirement.

Codex found a real bug I missed: the macOS branch of the board scan has been emitting % instead of board names under GNU findutils for as long as that line has existed. Codex fixed it as a drive-by; my branch still carries it. That is the single most consequential difference in the two diffs.

I have the better selection logic, Codex has the better test harness. Mine sorts the first level and picks items by number; Codex's runs the entire real setup script in a stubbed sandbox and can diff itself against the old flat menu for all 113 boards.

The trap both had to avoid

The task supplied 29 suffixes. Stripping the longest matching one repeatedly looks obvious and is wrong, because the suffixes overlap:

tang_primer_20k_dock_no_hdmi_no_tm1638

  longest match is _hdmi_no_tm1638   → tang_primer_20k_dock_no   a board that does not exist
  correct split   is _no_hdmi + _no_tm1638   → tang_primer_20k_dock

Both sides solved it, by opposite routes. I search all decompositions and keep the shortest remainder. Codex lets the regex engine do it: in a POSIX ERE, (…)+$ matches leftmost-longest, so the match starts as early as it still can while reaching the end of the string — which is exactly “strip as much as possible”. Codex's route is principled, not lucky, and it is one regex instead of a recursion.

Codex — second level

The two sides made opposite calls and each pays for it on the other screen. Codex's short first-level labels let select use two columns, so the whole board list fits a terminal; my count hints push it to one column and 57 lines. On the second level it reverses: my suffix-only labels fit two columns in 10 lines, while Codex repeats tang_nano_9k_ eighteen times down a single column.

One ordering difference is not a preference. Codex lists the first level in order of first appearance in the directory scan, so de0_nano_soc comes before de0_nano — because de0_nano_soc_vga666 sorts before de0_nano_vga666. I sort the derived board names, so de0_nano comes first. In a list people scan alphabetically, mine is the correct order.

The bug Codex found and I did not

The macOS branch of the board scan reads:

available_fpga_boards=$(find "$board_dir" ... -type d | xargs -I % -L 1 basename '%' | ...)

Under GNU findutils, -I and -L are mutually exclusive; xargs warns, drops -I, and prints the literal replacement string:

original darwin line -> first 6 entries: % % % % % %
codex's fixed line   -> first 6 entries: a7_lite_35t alinx_ax301 alinx_ax4010 ...

Codex deleted -L 1, which -I implies anyway. The reason they saw it and I did not is their test: it forces OSTYPE=darwin23 on Linux and runs the real discovery line, so the % list made a test fail. My test injects the board list directly and never touches that line. On a stock macOS with BSD xargs the old line is harmless, which is why this survived for so long — but anyone with GNU findutils ahead of /usr/bin on a Mac gets a menu of percent signs. I should take this fix.

How each side proved equivalence

The task asked for a check that the two-level selection is equivalent to the original. Both sides built one; they are instruments of different strength.

Claude's instrument

walk the menu, learn nothing in advance

The test extracts the menu section verbatim from the script, then explores it by typing numbers and reading what comes back. It never computes the expected grouping, so it cannot be fooled by a bug my own test code reproduces. It asserts that the reachable set equals the directory listing, that each board is reachable by exactly one pair of answers, and that nothing else is reachable.

Because it injects available_fpga_boards directly, it can test board lists that do not exist on disk: a directory named exit, a directory named back, hypothetical suffix combinations.

I mutation-tested it: deleting _no_hdmi from the list, and swapping the search for greedy longest-match, each make a named test fail.

Codex's instrument

run the whole script, and diff against the old one

The test builds a fake repository in a tempdir — 113 empty board directories, stub toolchain modules — and runs the real, unmodified 00_setup.source_bash inside it. That covers everything around the menu as well: the exact bytes of fpga_board_selection, the saved-selection bypass, the hackathon_top.sv override, the run-directory question, fpga_toolchain dispatch, and all four OSTYPE branches.

Its grouping oracle is independent of the suffix list: it derives the board models from boards/README.csv and groups by the longest catalog model that is a prefix.

And --baseline old_setup.source_bash replays every one of the 113 selections through both the old flat menu and the new two-level menu and demands identical output and identical selection files.

Codex's --baseline is the stronger claim, so I borrowed it. I rebuilt their stubbed-tempdir harness around my implementation and compared the original flat menu with my two-level menu for all 113 boards:

Pros and cons

Claude

pros

  • First level sorted by board name, so de0_nano precedes de0_nano_soc.
  • Items chosen by menu number, never by label text: a board directory called exit or back is selectable. The original menu could not do this either.
  • Count hint (18 configurations) tells the user a second menu is coming, and how big it is.
  • Second level shows only what differs, so 18 variants fit in 10 lines.
  • A board with one configuration is listed under its exact directory name — what you pick is what gets written to the selection file.
  • No subshell per board: 2.9× faster than Codex's function as written.
  • Test can inject board lists that do not exist on disk, and discovers the menu structure instead of assuming it.
  • Original user-visible strings preserved, so existing screenshots and course notes still match.

cons

  • Missed the xargs -I % -L 1 bug on the macOS path.
  • 294 added lines in the setup script against Codex's 152 for the same behaviour.
  • Recursive search is harder to read than one regex, and its worst case is exponential in the number of suffixes that match a tail (today: at most 5).
  • Four first-level labels are long and ugly (colorlight75b_tm1638_ecp5_yosys).
  • Count hints force a single column, 57 lines on the first screen.
  • Test never exercises the selection file, the toolchain dispatch, the hackathon override or the OSTYPE branches.
  • Same PS3 prompt on both levels, so the prompt line does not say which level you are on.
  • Keeps the typo “amoung” in the first-level prompt.

Codex

pros

  • Fixed the macOS xargs bug, found because the test forces every OSTYPE branch.
  • One regex instead of a recursion: shorter, and marginally the faster algorithm once the subshell is removed.
  • Half the code for the same behaviour.
  • Short first-level labels, so the 56 boards fit two columns and one screen.
  • Second level shows full directory names — unambiguous, and identical to what lands in fpga_board_selection.
  • Distinct PS3 per level (“Board (a number)” / “Variant (a number)”), so the prompt itself says where you are.
  • local PS3 REPLY: the function does not leak either variable.
  • Returns a status and lets the caller decide to exit, instead of calling exit from inside the menu.
  • Test runs the entire real script in a sandbox and checks the selection file byte for byte, plus the saved-selection bypass, the hackathon override and the toolchain dispatch.
  • Grouping oracle derived from boards/README.csv, independent of the suffix list.
  • --baseline compares old menu against new menu for all 113 boards.
  • Dropped the “amoung” typo from the prompt.

cons

  • First level in first-appearance order, so de0_nano_soc is listed before de0_nano.
  • Compares the label text, so a board directory named exit or back cannot be selected — it is read as the command.
  • $( ) per board makes the whole menu build 2.9× slower than it needs to be; the suffix array is also rebuilt on every call.
  • No hint that a board opens a second menu, so the user cannot tell a one-step choice from a two-step one.
  • Second level repeats the board prefix on every line: 18 variants in 18 lines.
  • Test's expected indices assume the unsorted order, so the suite is coupled to that choice; adopting sorted order means updating the oracle.
  • Its oracle raises ValueError for a new board directory missing from README.csv, so adding a board means touching the catalog first.
  • Reworded two user-visible messages, which invalidates existing screenshots and notes.
  • Relies on POSIX leftmost-longest matching in [[ =~ ]] — correct on glibc and BSD, but an unstated dependency on the platform regex engine.

What each side should adopt

Claude should take from Codex

  1. The xargs fix. Drop -L 1 from the darwin branch. One character range, and it repairs the board menu for any Mac with GNU findutils on PATH.
  2. The stubbed-tempdir harness. Running the real script against a fake boards/ tree costs 0.12 s per run against 2.4 s for the real repository — 20× — and it covers the selection file, the toolchain dispatch, the hackathon override and the OSTYPE branches — all of which my test skips entirely.
  3. --baseline. Fold the old-versus-new comparison into the test file instead of leaving it as the one-off script I wrote for this report, so the equivalence claim is re-checkable by anyone.
  4. The independent oracle. Grouping expectations derived from boards/README.csv rather than from the suffix list — it catches a wrong grouping that a suffix-based expectation would happily confirm.
  5. Per-level PS3, and local PS3 REPLY. Cheap, and the prompt then tells the user which level they are answering.
  6. Return a status instead of calling exit. Leaving the exit decision to the caller is the cleaner contract.
  7. Consider _ecp5_yosys, or an equivalent, so the four Lattice entries read karnix rather than karnix_ecp5_yosys.

Codex should take from Claude

  1. Sort the first level. One sort -u over the derived names puts de0_nano before de0_nano_soc. Their test's expected indices need the same sort applied to the oracle.
  2. Select by number, not by label. Comparing $REPLY against the item count removes the exit/back collision for good, and it is no longer code than the string comparison.
  3. Return through a variable, not $( ). Same algorithm, 2.9× faster menu build. Hoisting the 33-element suffix array out of the function saves a little more.
  4. A hint that a second menu follows. Some marker on the multi-configuration entries — even a bare asterisk, which would keep the two-column layout.
  5. Shorten the second level to the distinguishing suffix, so 18 variants do not consume 18 lines.
  6. Walk the menu in at least one test rather than computing the indices, so the test cannot agree with a wrong grouping; and inject synthetic board lists, including names that collide with menu commands.
  7. Mutation-test the suffix logic. Removing _no_hdmi should make a named test fail; it is the cheapest proof that the test has teeth.

Both should fix

The menu numbering is locale-dependent, and neither side noticed. The board list comes from sort, whose collation follows the locale:

LC_ALL=C          -> item 26 = de23_lite   item 27 = de2_115
LC_ALL=en_US.UTF-8 -> item 26 = de2_115     item 27 = de23_lite

Two boards swap places, so “choose number 26” means different things on a C-locale machine and a UTF-8 one. That matters for a course where an instructor reads numbers out loud. LC_ALL=C sort (or LC_COLLATE=C) fixes it for both, and the original flat menu has the same flaw. I checked the related worry — whether locale collation could make sort -u silently merge two distinct board names — and it does not on this glibc: all 56 names survive under C, en_US.UTF-8 and ru_RU.UTF-8.

If the two were merged

The best single version is mostly Codex's shape with my selection logic: their regex and their 152-line footprint, their per-level prompts and status-return, their test harness and --baseline; my sorted first level, number-based selection, variable-return calling convention, short second level and count hints; their xargs fix; and LC_ALL=C on the sort, which neither has. The grouping needs no reconciliation at all — both already produce the same 56 boards.
