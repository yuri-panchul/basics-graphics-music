Requirement by requirement

R1 altera / intelFPGA no longer indicate old / new confirmed, and worse than stated

The current script treats altera as the old-version directory and intelFPGA_lite / intelFPGA as the new one. On this machine ~/altera/ does hold 13.0sp1 and 13.1 — but the parent directory is not evidence of anything, and neither is the version directory name:

~/altera_lite/25.1std -> "Version 25.1std.0 ... Lite Edition"

So a directory called _lite holding a version called std contains the Lite edition. Any rule built on names is guessing. quartus_sh --version is the only authority, and it also reveals that 13.x calls itself Web Edition — the old name for Lite, which the free-edition test must accept as well.

R2, R6 DE23-Lite is Agilex 3, not Arria correction

R6 calls it “Arria board DE23”. The board file says otherwise:

boards/de23_lite/board_specific.qsf: DEVICE A3CZ135BB18AE7S -> Agilex 3

The Pro installation carries Agilex 3 support (three agilex3_* board presets). The useful consequence is that no special case is needed for DE23-Lite: Agilex 3 exists only in the Pro line, so a correct compatibility filter leaves Pro as the only candidate and selects it on its own. R6's “DE23 should be used with Pro clearly” falls out of the algorithm instead of being bolted onto it.

Note also that the board is currently listed in 00_setup.source_bash among the boards with use_old_version_of_quartus=0, which under the present script means “prefer intelFPGA_lite” — i.e. today it asks for a Lite install that cannot target the part.

R3 Cyclone II needs 13.0sp1 specifically, not “13.0sp1 or 13.1” correction

13.1 dropped Cyclone II. Measured from the device-support directories:

13.0sp1 devinfo/ ... cycloneii cycloneiii cycloneive cyclonev maxii maxv ... 13.1 devinfo/ ... cycloneiii cycloneive cyclonev maxii maxv

So the three boards split rather than forming one group: DE1 (EP2C20) and DE2 (EP2C35) can only use 13.0sp1, while DE0 (EP3C16) can use 13.0sp1 or 13.1 and should take 13.1 under the newest-compatible rule. A single “old versions” bucket cannot express this, which is the core reason the mechanism has to change rather than be patched.

Minor: R3 writes “DE2 (without 114)”; the board with the suffix is DE2-115.

R3+ A board the requirements do not cover: Cyclone I gap

marsohod_mcy112 is EP1C12Q240C8 — original Cyclone, a generation older than anything R3 mentions. Neither installed 13.x carries a cyclone family directory, and 13.0sp1's legacy/ folder holds only ACEX, APEX, FLEX and MAX 9000 descriptors. The board is currently mapped to the “old” bucket, which will hand it 13.1 — a version that cannot target it.

I cannot tell from here whether this is a version limit or simply device support that was never installed. Either way the new code should say so rather than pick something that fails later in synthesis.

R4 MAX 10 is missing from the Lite install too correction

R4 is right that MAX 10 is absent from 13.x. It is also absent from 25.1std on this machine:

25.1std devinfo/ cyclone10lp cycloneive cycloneivgx cyclonev maxii maxv # no max10

Quartus Prime Lite 25.1 does support MAX 10, so this is missing device support in the installation, not a version limit. The practical effect is that DE10-Lite cannot be built on this machine right now, and that is a fact the script should report clearly. It is also the strongest argument for the design below: compatibility must be computed from what is installed, not from a table of what each version could in principle support.

R5 Free edition beats recency; recency beats everything else confirmed, implementable

Unambiguous and expressible as a sort key. With what is installed here, the rule means 25.1std (Lite) wins over 26.1.1 (Pro) for every board either can build — which is every Cyclone IV and V board in the repository.

R6 Standard over Pro, but only within a version needs your decision

No Standard edition is installed here, so this preference cannot be tested on this machine — it will be written from the specification and left unexercised. R6 also says the preference applies “within the same version or its version is more recent”, which reads two ways. I plan to implement the simpler reading: Standard and Pro are ranked only when their versions are equal; otherwise the newer version wins. See the decision list at the end.

The design that follows

The present code asks one yes/no question per board — use_old_version_of_quartus, set from a hardcoded list of board names in 00_setup.source_bash. R3 alone breaks that: DE1 and DE0 are both “old” and need different versions. So the flag goes, and with it the board list.

Each board states its own requirement

Every Altera board already declares its exact part in its own board_specific.qsf, and the setup script already knows $fpga_board. Reading the device from the board directory removes the hardcoded list entirely and cannot drift out of date when a board is added.

Each installation states what it can build

For the standard release line the installed families are directory names under <root>/quartus/common/devinfo/, which matched reality exactly in every case I tested — including the two that a version table would have got wrong (13.1 without Cyclone II, 25.1std without MAX 10). The Pro line keeps its device data under <root>/devices/ instead, grouped by process node, so Pro needs its own small mapping.

One attractive-looking shortcut is wrong and I want it recorded so nobody tries it again: quartus/linux64/pgm_parts.txt exists in every installation and lists part names, but it is the programmer's JTAG device list, not the synthesis device support. It claims 13.1 knows EP2C20F484C7, which 13.1 cannot synthesise for.

Selection, in order

  1. If QUARTUS_ROOTDIR is set and usable, take it and stop — the explicit override, exactly as now.
  2. Otherwise collect candidate installation roots from INTEL_FPGA_HOME, ALTERA_HOME, QUARTUS_HOME, then the standard parents, under every vendor directory name: altera, altera_lite, altera_pro, intelFPGA, intelFPGA_lite, intelFPGA_pro.
  3. For each candidate, read its version and edition from quartus_sh --version and its installed families from the device data. Cache the answers — one probe per installation, not per board.
  4. Map the board's device to a family, and keep only installations whose installed families include it. This is the step that makes R2, R3 and R4 work without special cases.
  5. Sort the survivors by, in order: free edition first (Lite or Web before Standard or Pro); then newest version; then Standard before Pro. Take the first.
  6. If nothing survives, fail with a message naming the board's part and family, which installations were examined, and what each one does support — so that “install MAX 10 support in 25.1std” is obvious from the error rather than discovered during synthesis.

Worth stating plainly: on this machine that algorithm sends DE1 and DE2 to 13.0sp1, DE0 to 13.1, every Cyclone IV and V board to 25.1std, DE23-Lite to 26.1.1 Pro, and reports a clear failure for DE10-Lite and marsohod_mcy112. The last two are real gaps in the installation, not in the script.

Order of work

  1. Build the harness first. Stub helpers, fake installation trees, and a table of board → expected version, so the selection rules are testable before the rewrite exists. Also exercise the real four installations.
  2. Rewrite the discovery in scripts/steps/00_setup_intel_fpga.source_bash: probe, cache, filter, sort. Commit on its own.
  3. Remove use_old_version_of_quartus and its board list from 00_setup.source_bash, and from scripts/admin/generate_all_packages.bash, which also sets it. Separate commit, because this one touches shared files.
  4. Rename our own variables per R9. Separate commit, so the rename is a diff you can skim rather than read.
  5. Verify by actually synthesising: a Cyclone IV board on 25.1std and, if you want the old path proven, DE0 on 13.1. I can run these here.
  6. Generate the board table as quartus_boards.html, .md and .csv in a local directory, outside the repository unless you want them committed.

What I need from you

1. R6, the Standard versus Pro reading

Confirm the simple reading: rank Standard above Pro only when the versions are equal, and otherwise let the newer version win. The alternative reading — that Standard also wins when it is newer — is the same thing, so the only case in doubt is a newer Pro against an older Standard, where I propose the newer Pro wins.

2. The unverifiable table columns

Manufacturer, LE count and year of introduction come from me, not from the repository. Shall I mark them as unverified in the output, or leave the table looking uniform?

3. Two boards with no usable toolchain

DE10-Lite needs MAX 10 support installed into 25.1std; marsohod_mcy112 needs a Quartus old enough for original Cyclone, which may be older than 13.0sp1. Do you want the script to fail loudly for these, or to keep today's behaviour of choosing something and letting synthesis fail later? I recommend failing loudly.
