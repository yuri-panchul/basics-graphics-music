Two errors of mine, and the method that caused them

my error 1 I said MAX 10 was missing. It is installed. retracted

You are right that every release from 14.0.2 onwards supports MAX 10. It is present in both Lite installations here, so DE10-Lite builds normally and there is nothing to fix. My revision 1 claim was wrong.

The cause was my method. I read the device families from the directory names under <root>/quartus/common/devinfo/, and MAX 10 has no directory of its own there — its data sits under an internal codename:

devinfo/55nm/zb50_non_vr_analog/ddb_zb50_non_vr_analog.pll # zb50 = 10M50

That mechanism is therefore discarded. It happened to agree with reality for Cyclone II in 13.1, which is what made it look trustworthy.

my error 2 I missed the installation in /opt corrected

I looked only under $HOME. The current script already searches /opt and /tools as well, so /opt/intelFPGA_lite/21.1 was always a candidate and I should have enumerated the same places the script does. It matters: 21.1 is a second Lite edition, and the free-edition preference has to choose between it and 25.1std.

The mechanism that is actually correct

Ask the tool. The device Tcl package answers both questions authoritatively, for every edition including Pro: 

load_package device
puts [get_family_list]                                  # families
puts [expr {[lsearch -exact [get_part_list] $part] >= 0}]  # this exact part?

Two mechanisms are recorded here as rejected, so that nobody tries them again:

  • quartus/linux64/pgm_parts.txt exists in all five installations and lists part names, but it is the programmer's JTAG list. It claims 13.1 knows EP2C20F484C7, which 13.1 cannot synthesise for.
  • devinfo/ directory names, as above — incomplete, because some families are stored under internal codenames.

Cost of the real probe, measured: 0.9 s for 25.1std, 1.8 s for 13.1, 5.0 s for Pro 26.1.1. About ten seconds for all five, which is far too slow to repeat on every lab invocation and is the reason the design below caches.

The design

Today the code asks one yes/no question per board, use_old_version_of_quartus, from a hardcoded board list in 00_setup.source_bash. R3 breaks it on its own, and EP3C120F780C6 breaks any version-based replacement. Both go.

Each board states its own requirement

Every Altera board already declares its exact part in its own board_specific.qsf, and the script already knows $fpga_board. Reading the device from the board directory deletes the hardcoded list and cannot drift when a board is added.

Each installation is asked what it can build

One quartus_sh -t probe per installation returns its version, edition and part list. Results are cached, keyed by the installation path and the timestamp of its quartus_sh, so the ten seconds are paid once rather than on every lab.

Selection, in order

  1. If QUARTUS_ROOTDIR is set and usable, take it and stop — the explicit override, as now.
  2. Otherwise collect candidate roots from INTEL_FPGA_HOME, ALTERA_HOME, QUARTUS_HOME, then $HOME, /opt, /tools, under every vendor directory name: altera, altera_lite, altera_pro, intelFPGA, intelFPGA_lite, intelFPGA_pro.
  3. Probe or read from cache: version, edition, part list.
  4. Keep only installations whose part list contains the board's exact part. This single step delivers R2, R3, R4 and both unbuildable boards.
  5. Sort the survivors: free edition first (Web or Lite ahead of Standard or Pro); then newest version; then Standard ahead of Pro at equal versions. Take the first.
  6. If none survive, fail naming the board's part, which installations were examined, and what each supports — so “this part needs a licensed 13.x” is visible immediately rather than discovered during synthesis.
