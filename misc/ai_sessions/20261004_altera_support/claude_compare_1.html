Which Quartus, and Who Is Right

Two rewrites of the code that decides which installed Quartus can build a board. They agree on most boards. Where they disagree, I settled it by compiling for the disputed device rather than by reading documentation — and on the question that matters, I was wrong.

The short version

Both part tests are wrong, in opposite directions. Mine asks whether the part is in get_part_list and so refuses dk_dev_3c120n, a board that in fact compiles. Codex asks get_part_info -family, which answers yes for parts an installation cannot build at all — so codex's correct answers for the old boards come from its hand-written table of family and version limits, not from its probe.

There is a rule that needs no table and is right on every case I could verify: the part is buildable if it appears in get_part_list, or if its family appears in get_family_list. That is what I am adopting.

Beyond that, I lose the precedence of ALTERA_HOME and its siblings, I do not deduplicate installations, and worst of all I take a quartus found on PATH without checking it at all. Codex re-probes on every invocation — 4.19 s against my 0.13 s — and does not honour QUARTUS_ROOTDIR when it cannot build the board, contrary to the instruction I was given.

How the search works, in plain English

Both implementations follow the same outline. The steps run in order and the first that produces an answer wins. Where they differ, the difference is marked.

  1. 01

    Find out what the board needs

    Read the device string out of the board's own Quartus project file, boards/<board>/board_specific.qsf — for example EP4CE115F29C7 for DE2-115. Both read it as plain text rather than executing the file, and neither keeps a list of board names, so adding a board needs no change to the search.

  2. 02

    If QUARTUS_ROOTDIR is set, that is the installation

    It names one installation directly, so there is nothing to search.

    this is where they part company

    claude uses it whatever happens, and warns if that Quartus does not list the board's part. codex puts it through the same compatibility test as everything else: if it fails, codex abandons it and carries on searching.

  3. 03

    If quartus is already on the PATH, leave it alone

    Someone who has set up their own environment is assumed to mean it. Both check that the executable really sits in a quartus/bin or quartus/bin64 directory, and warn rather than guess if it does not.

  4. 04

    Otherwise look in the usual places

    First wherever INTEL_FPGA_HOME, ALTERA_HOME or QUARTUS_HOME point, then $HOME, /opt and /tools — or the C:, D: and E: drives under Windows. In each, directories named altera, altera_lite, altera_pro, intelFPGA, intelFPGA_lite and so on, each holding version directories.

    A directory counts as an installation only if the Quartus executables are actually in it.

    they part company again

    codex treats the locations as ranked tiers and stops at the first tier that yields anything usable, so the place you pointed at wins even if somewhere further down the list has something newer. claude pools every location together and picks the globally best, which means it can quietly ignore where you pointed.

  5. 05

    Ask each installation whether it can build this part

    Not which families it supports — which part. The distinction is not academic: both installations of Quartus II 13 support the Cyclone III family, and only one of them can build the particular Cyclone III on the dk_dev_3c120n board.

    Neither implementation looks at a licence. They ask the tool and believe the answer.

    the difference that actually matters

    The two ask different questions, and get different answers. See the next section.

  6. 06

    Among those that can, pick the best one

    A free edition wins over a paid one even when it is older, because a student who has Lite installed should not be sent to Pro. Then the newer version wins. Then, only when two versions are equal, Standard comes before Pro. Both implement this identically.

  7. 07

    If nothing can build it, say so

    The message names the board, the part, and what was found, so that the missing piece is visible at once instead of surfacing as a confusing failure later in synthesis.

The question each one asks, and the experiment that settles it

Run on the same installation, Quartus II 13.1, for the same part: 

# codex
get_part_info -family EP3C120F780C6     → {Cyclone III}   # usable

# claude
lsearch -exact [get_part_list] EP3C120F780C6   → -1        # not usable

Documentation would not have settled that, so I built a one-gate project for the device and compiled it with 13.1: 

$ quartus_map t
Info: Quartus II 32-bit Analysis & Synthesis was successful. 0 errors, 1 warning

$ quartus_fit t
Info (170137): Fitter placement was successful

So get_part_list returns a narrower set than the tool can actually target, and my test rejects a board that works. That is a real defect in my implementation, not a difference of taste.

For completeness I ran the same experiment on the other board that neither implementation accepts, marsohod_mcy112 with its Cyclone I device: 

$ quartus_map t      # EP1C12Q240C8 on 13.0sp1
Error (20005): A license file is required to enable compilation of your design
               for the Cyclone family of devices

Here both are right to decline, by different routes: codex from its table, which caps Cyclone I at a much older release for a free edition, and mine from the part list. Neither inspects the licence; the tool simply refuses.

A rule that needs no table

The last column of the table above is the discriminator. A part is buildable when: 

the part is in  get_part_list        # the installation offers it outright
            or
the part's family is in  get_family_list   # the installation has that family installed

That is right in all six rows, and in every other case I tested. It accepts EP3C120F780C6 on 13.1, because Cyclone III is installed there; it refuses a Cyclone II on 13.1 and on 25.1std, because that family is not; it refuses Cyclone I on 13.0sp1 for the same reason; and it refuses Agilex 3 on a Lite installation, which does not even know the part. No family list, no version limits, no board names — both facts come out of the same single probe per installation, so it costs nothing extra.

One detail cost me a wrong conclusion for several minutes and is worth recording: get_part_info -family returns a one-element Tcl list, so comparing it against get_family_list with lsearch -exact fails unless you take [lindex $raw 0] first. My first run of this experiment reported that the rule did not work, when in fact my Tcl did not.

The PATH case, which is worse than everything above

Put a Quartus on PATH that cannot build the board — 25.1std, with de1 and its Cyclone II: 

# codex
WARNING: Skipping Quartus '$HOME/altera_lite/25.1std/quartus'. Lite 25.1.0.1129 is
         incompatible with EP2C20F484C7 or the wrapper's version limit.
WARNING: Skipping Quartus '$HOME/altera/13.1/quartus'. Web 13.1.0.162 is incompatible ...
WARNING: Skipping Quartus '$HOME/altera_pro/26.1.1/quartus'. Pro 26.1.1.130 is incompatible ...
WARNING: Skipping Quartus '/opt/intelFPGA_lite/21.1/quartus'. Lite 21.1.1.850 is incompatible ...
INFO:    Selected Quartus Web 13.0.1.232 for 'de1' (EP2C20F484C7) ...
         QUARTUS_ROOTDIR=$HOME/altera/13.0sp1/quartus

# claude
CHOSEN $HOME/altera_lite/25.1std          # silently wrong, no warning at all

Codex treats PATH as a hint: tier two of the search, subject to the same test as everything else, and when it fails the search moves on and lands correctly on 13.0sp1. Four warnings on a successful run is noisy, but each one says exactly why it skipped.

Mine takes PATH unconditionally, with no compatibility check and no warning of any kind, and proceeds with a Quartus that cannot build the board. The failure then appears much later, as a device error in synthesis, pointing nowhere near its cause.

What marks this as an oversight rather than a decision: my QUARTUS_ROOTDIR branch does probe and does warn. The PATH branch simply omits the same check. It is also the more dangerous of my two defects:

A worked example of the tier difference

The same shape of problem appears with the override variables. Point ALTERA_HOME at a directory holding only the oldest Quartus, while $HOME holds four including the newest, and ask for a board that all of them can build: 

ALTERA_HOME=$TMP/oldonly   holds:  13.0sp1
$HOME                      holds:  altera/13.0sp1  altera/13.1
                                   altera_lite/25.1std  altera_pro/26.1.1
board zeowaa needs EP4CE6E22C8, which all four can build

# codex
Selected Quartus Web 13.0.1.232 ... using ALTERA_HOME='$TMP/oldonly'

# claude
using Quartus Lite from '$HOME/altera_lite/25.1std'

Codex walks the locations as ranked tiers and stops at the first that yields anything usable: QUARTUS_ROOTDIR, then PATH, then INTEL_FPGA_HOME, then ALTERA_HOME, then QUARTUS_HOME, then the default places as one tier. The newest-version preference applies within a tier, so tier four wins outright and 25.1std is never considered. Mine pools all six locations and sorts globally, which turns ALTERA_HOME from an instruction into merely one more place to look.

Why codex is right: someone setting ALTERA_HOME usually means “use that tree” — to reproduce a build with a particular version, or because the newer installation is incomplete. If something newer elsewhere can overrule it, the variable has no force at all.

Five divergences. Codex is right about three of them. I am right about one, and only because you told me which behaviour you wanted for QUARTUS_ROOTDIR, not because it follows from anything in the tools. The fifth, the part test, neither of us gets right on its own.

The two implementations

codex_quartus

886 lines · 14 functions · 309 lines of tests

Advantages

  • The part test is correct, which is the whole job. get_part_info -family matches what the tool can really compile.
  • Keeps the precedence of the override variables. INTEL_FPGA_HOME, then ALTERA_HOME, then QUARTUS_HOME, then the default places, each tried as a tier. That is what the original script did and what the brief asked to preserve.
  • Deduplicates and canonicalises installation paths with readlink -f, so the same Quartus reached two ways is considered once.
  • Requires all three executables — the GUI, the shell and the programmer — and skips an incomplete installation rather than choosing it and failing later.
  • Scopes QUARTUS_ROOTDIR around each probe, so an inherited value cannot make one installation answer questions about another.
  • Translates paths with cygpath under Cygwin and MSYS, where a Unix path handed to the Windows tool would not resolve.
  • Validates the device string in the Tcl helper before using it.
  • Ships tests and documentation: a Python suite and 57 lines of README.
  • Found a board I missed — alinx_ax301 was absent from the toolchain list in 00_setup.source_bash, and codex added it.
  • Finished the job: it removed use_old_version_of_quartus from the shared files in the same commit.

Disadvantages

  • The table is doing the real work. Its probe, get_part_info -family, answers yes for parts the installation cannot build, so correctness for the old boards rests on the hardcoded limits rather than on asking the tool.
  • Carries a hand-written table of family and version limits — Cyclone I, II, III caps, Agilex needing Pro, MAX 10 needing 14.0 and later — which is exactly the kind of knowledge the rewrite was meant to stop encoding by hand, and which can fall out of step with reality.
  • Still has a board-name special case, omdazz_epm570_quartus_13_1_or_older, hardcoded in the compatibility function.
  • No caching. Every lab command re-probes every candidate: 4.19 s against 0.13 s, and it grows with the number of installations.
  • Does not honour QUARTUS_ROOTDIR when the installation cannot build the board, contrary to the instruction to trust an explicit override and warn.
  • Chatty: a warning for every installation it skips, so a machine with five Quartus versions prints several warnings on a normal, successful run.

claude_quartus

871 lines · 12 functions · no committed tests

Advantages

  • No table of any kind. No family limits, no version limits, no board names. Everything comes from the board's own project file and from the installation itself, so there is nothing to maintain as devices and releases come and go.
  • Caches what it learns, keyed by the timestamp of quartus_sh, so the cost is paid once and a normal run spends 0.13 s instead of 4.19 s. That is 32 times faster on every single lab command.
  • Trusts an explicit override and says plainly that synthesis may fail, which is the behaviour asked for.
  • Quieter and smaller: one line naming the chosen edition and directory, 12 functions rather than 14, and no Bash arrays.
  • Nothing is passed into Tcl, because the part list is fetched once and searched in the shell, so there is no device string to validate.

Disadvantages

  • A quartus on PATH is taken without any check and without a warning, so the wrong tool gets used silently. The most dangerous defect of the two, because it is quiet and common.
  • The part test is wrong, and it is the central mechanism. It rejects dk_dev_3c120n, a board that builds.
  • Loses the precedence of the override variables by pooling every location and taking the global best, so pointing ALTERA_HOME somewhere can be silently overruled.
  • Does not deduplicate: with ALTERA_HOME=$HOME it finds nine installations where there are five, and probes each twice.
  • Does not canonicalise paths, which is why the duplicates slip through.
  • Does not scope QUARTUS_ROOTDIR when probing, so an inherited value could in principle redirect the answer.
  • No cygpath handling, so the Tcl file path may not resolve under Cygwin and MSYS.
  • Checks only quartus_sh when deciding that a directory is an installation, leaving a missing programmer to surface later.
  • No committed tests and no documentation; the harness I used lives outside the repository.
  • Unfinished: use_old_version_of_quartus is still set in the shared files, now dead, and the alinx_ax301 gap is still there.

What I should change

In order of how much it matters:

  1. Check the PATH installation like any other, and when it cannot build the board, say so and carry on searching instead of using it in silence.
  2. Replace the part test with the two-part rule: the part is in get_part_list, or its family is in get_family_list. Both come from the one probe already being made, so the cache and the speed survive, and no table appears.
  3. Restore the tiers. Try INTEL_FPGA_HOME, then ALTERA_HOME, then QUARTUS_HOME, then the default places, and stop at the first tier that yields a usable installation, instead of pooling them.
  4. Canonicalise and deduplicate installation paths.
  5. Scope QUARTUS_ROOTDIR around each probe, and require all three executables before calling a directory an installation.
  6. Add cygpath translation for Cygwin and MSYS.
  7. Commit the harness as a test, and add the alinx_ax301 entry and the removal of use_old_version_of_quartus from the shared files.

Keep from mine: no tables, the cache, and honouring an explicit override with a warning. Take from codex: everything in the list above. The result is codex's correctness with my absence of hardcoded knowledge, which is better than either as it stands.

Both implementations run through harnesses with stubbed info, warning and error helpers against the five installations on this machine: altera/13.0sp1 and 13.1, /opt/intelFPGA_lite/21.1, altera_lite/25.1std, altera_pro/26.1.1.
The disputed devices were settled by building a one-gate project with quartus_map and quartus_fit, not from documentation. Timings measured with /usr/bin/time on a warm cache.
