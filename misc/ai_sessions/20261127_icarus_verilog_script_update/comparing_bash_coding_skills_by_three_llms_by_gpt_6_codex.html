Assessment

There is no unconditional winner in these four files. Codex is the most direct implementation of a complete native Icarus command file. Grok is the most capable of the two lab-only line readers in the cases tested. Claude offers a simpler line reader with clear explanations of Bash compatibility choices.

The tradeoffs are consequential. Codex gives the list full control over dependencies and compilation order, but changes header lookup precedence and rejects a list without a final newline on the installed Icarus 12. Claude and Grok preserve the compilation working directory and tolerate that final-line case, but always append shared sources, reject absolute source paths, and cannot read native Icarus options. Grok additionally handles whole-line comments and surrounding whitespace; Claude does not.

Engineering approaches: pros and cons

These observations distinguish demonstrated behavior from design intent. A portability idiom in the source is not treated as proof of native Windows or macOS support.

Claude — A conservative line reader

Pros

  • Keeps compilation in run/. Existing relative compiler context and header precedence remain intact. Claude L154
  • Uses Bash arrays rather than command-string evaluation. Quoted array elements preserve embedded spaces and avoid shell word splitting; the source-name-with-spaces fixture passed.
  • Preserves listed order. Nested package and module dependencies compile in the specified sequence, with no sorting or filesystem rediscovery of lab files.
  • Handles CRLF and a missing final newline. IFS= read -r, the EOF guard, and CR removal are deliberate, useful details. Claude L135
  • One compiler command to maintain. The fallback retains baseline ordering: lab SystemVerilog, shared SystemVerilog, then lab Verilog.
  • Explains non-obvious Bash expansions. Both CR removal and the empty-array compatibility expansion have nearby comments. The latter expresses an older-Bash compatibility intent; only Bash 4.4 was exercised here.

Cons and limits

  • No comment or whitespace normalization. A # or // line, or a whitespace-only line, becomes a path. These probes failed. Claude L141
  • Blind path prefixing breaks absolute paths. /tmp/…/core.v becomes ..//tmp/…/core.v. Claude L143
  • Only lab sources are controlled by the list. Unlisted shared files still compile. Explicitly listing a shared file compiles it twice; the duplicate-module fixture failed.
  • Limited ordering across directories. Shared packages remain after the lab sources unless named explicitly, which then risks duplication. The shared-package-order fixture failed.
  • No native command-file grammar. +define+, +incdir+, nested -f, block comments and trailing comments are treated as filenames.
  • Minor clarity issues. lab_sv_files also holds listed .v entries. The comment does not expressly warn that common/peripheral files remain automatic. All modes still clear the caller’s nullglob setting, an inherited behavior.

Codex — Delegate parsing to Icarus

Pros

  • One authoritative dependency list. No extra lab or shared source globs are appended in list mode. Unlisted invalid shared files are excluded, and shared files can be listed exactly once. Codex L120
  • Controls package order across the whole design. Both lab-package and shared-package ordering fixtures passed.
  • Native format support with little shell code. Icarus handles hash/slash/block/trailing comments, ordinary +incdir+, +define+, nested lists and absolute paths in the successful probes.
  • Contains the directory change. A subshell compiles from the lab and explicitly writes run/a.out; assembly, memory loading and simulation remain in run/. Codex L126
  • Leaves the fallback command intact. The original globs, include paths, top selection and language selection remain for labs without a file list.
  • Smallest net change in this file. Fifteen added net lines, without a custom parser or array-compatibility expansion. List mode also leaves the caller’s nullglob state alone.

Cons and limits

  • Confirmed header-precedence regression. When both lab and run/ contain the same included header, this branch selects the lab copy while baseline, Claude and Grok select the run copy. -I run does not preserve the old result on Icarus 12. Codex L127
  • Fails on a final filename without a newline. The native parser reports File name not terminated; both line-reader implementations accept the same file.
  • Requires a complete list. Existing lab-only lists that depend on automatic common/peripheral modules fail. This is intentional under its contract, but requires migration and clear documentation.
  • Changes the shared meaning of .f. An Icarus-specific command file with options is not necessarily usable by the existing Vivado line reader. A cross-tool format policy is needed.
  • Inherits native parser limitations. An unquoted space in the tested +incdir+include files form fails on Icarus 12, although a source filename with a space succeeds. Native parsing does not imply every whitespace case works.
  • Two compiler invocations must remain aligned. Later changes to flags need to be applied to both branches. The explicit run/a.out path also assumes the existing lab/run layout.

Grok — A more tolerant lab-only reader

Pros

  • Handles ordinary human-edited lists better than Claude. It removes surrounding whitespace and skips empty, whole-line # and whole-line // comments. Those fixtures pass. Grok L136
  • Retains the good line-reader properties. CRLF, an unterminated final line, embedded filename spaces, ordered dependencies and the original compilation directory all work in the probes.
  • Names the contract clearly. The comment explicitly says common/peripheral sources are still compiled after listed lab sources. Grok L120
  • Uses explicit array declarations and neutral names. local -a lab_sources matches the fact that a list may mix .sv and .v.
  • One compiler command and no external text filters. Parsing uses Bash built-ins, with the same older-Bash empty-array idiom as Claude. No shell evaluation of list contents is introduced.

Cons and limits

  • Absolute paths and native options still fail. Every accepted line receives ../; options and nested lists are not recognized. Grok L144
  • Comment support is partial. Trailing // and multiline /* … */ comments fail. The broad comment “comments are skipped” should name the supported forms.
  • Shared-source duplication and ordering limits remain. It has the same implicit-shared contract and failures as Claude when lists include shared files or need a shared package first.
  • Dense expansions lack the required explanations. The CR stripping and two nested whitespace-trimming expansions have no immediately preceding explanatory comments, contrary to the target repository’s style rule. Grok L136
  • More custom grammar to maintain. Adding quoted paths, inline comments or options would further complicate the parser. Trimming also deliberately discards leading/trailing whitespace in literal filenames.
  • Inherited shell-option leakage remains. nullglob is always disabled afterward, even if it was enabled by the caller.

Findings that affect use or maintenance

F01Behavior regression · Codex

Compilation CWD changes the winning header

The same `include "collision.svh" selects RUN in the baseline, Claude and Grok, but LAB in Codex. Both files exist and contain different definitions. All simulations complete, so this is a semantic regression rather than a syntax error. A generated run-directory configuration could be shadowed by a lab copy.

Recommended action: Treat header lookup order as an explicit requirement. Preserve it with a verified compiler strategy or document an intentional change; the current -I run alone is insufficient.

Reproduction: include_precedence

F02Robustness gap · Codex

The last line must end with a newline on the tested compiler

A file containing exactly tb.sv, without a final newline, is accepted by Claude and Grok but rejected by Icarus 12 through Codex’s native parser. The error is sv_file_list.f:1: ERROR: File name not terminated.

Recommended action: Normalize the terminating newline without changing path semantics, or reject it with a clear actionable diagnostic and document the requirement. Add this case to the regression suite.

Reproduction: no_final_newline

F03Contract-dependent failure · Claude and Grok

Explicit shared sources can be compiled twice

A list containing ../../common/shared.sv followed by the testbench causes both line readers to pass that source explicitly and again through the common-source glob. The real compiler reports duplicate module declarations. A shared package that must precede the lab can similarly collide with the automatic pass.

Recommended action: Choose complete-list semantics, or deduplicate canonical source paths while defining the intended global order. If lists must never name shared files, document and diagnose that restriction.

Reproduction: explicit_shared

F04Path-format limitation · Claude and Grok

Absolute paths are converted into invalid relative paths

Both parsers prepend ../ to every nonempty accepted record. The absolute-path fixture therefore fails even though the source exists. Codex accepts it through the compiler.

Recommended action: Either explicitly limit the format to relative paths, or distinguish absolute paths on each supported platform before prefixing. This test establishes Unix behavior only.

Reproduction: absolute_path

F05Input-format limitation · Claude

Comment lines and padding become source paths

Whole-line hash comments, slash comments, and a whitespace-only line each cause compilation to stop. The parser strips one trailing CR but otherwise preserves the line verbatim.

Recommended action: Define a plain-filename format clearly, or add consistent trimming and documented comment forms. Grok provides the stronger tested starting point for this contract.

Reproduction: hash_comments

F06Input-format limitation · Grok

The comment grammar is narrower than the comment suggests

Whole-line comments work, but tb.sv // comment and multiline block comments fail. The description “comments are skipped” does not communicate the boundary.

Recommended action: State “whole-line # and // comments” explicitly. Supporting a native command-file grammar calls for native parsing or a carefully specified parser, not incremental ad hoc stripping.

Reproduction: inline_comment

F07Compiler limitation exposed · Codex

Native +incdir+ does not cover every space-containing path

On installed Icarus 12, +incdir+include files produces files: No such file or directory. The corresponding no-space include-directory fixture passes, as does a source filename containing a space. Claude and Grok do not support either +incdir+ form.

Recommended action: Document the tested compiler boundary and verify any proposed encoding or workaround against the supported Icarus releases. Do not generalize source-filename handling to option values.

Reproduction: incdir_spaces

In long shell code blocks, put `then` on its own line after `if` and `elif`
conditions instead of using `; then` on the condition line.

In Bash scripts, separate comment blocks from adjacent non-comment code with

This exception does not apply to function definitions or bodies, `if`
statements, or loops. Keep consecutive comment lines together.

(`for`, `while`, or `until`).

## Bash parameter expansion and spacing

Explain non-obvious Bash parameter expansions with a comment immediately
above each assignment or command, describing the operator and its effect.
Keep each comment and its code together, separated from surrounding code by
empty lines. Do not add an empty line before a closing `fi`, `done`, `esac`,
or function brace just to separate such a pair.

Do not put an empty line immediately after an opening `then`, `do`, or
function `{`, even when the first item is a comment. This takes precedence
over the comment-separation rules above.

following single-line command or assignment.

single-line command, or assignment.
