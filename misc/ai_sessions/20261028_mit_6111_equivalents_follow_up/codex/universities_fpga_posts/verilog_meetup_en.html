From the first FPGA demonstration to a reviewable engineering project

A learning group can use a public curriculum comparison as a menu of exercises. The aim is not to collect course names, but to produce work that another engineer can inspect: a specification, an implementation, a checker and an explanation of the trade-offs.

The questions follow the interview observations in Yuri Panchul’s EDA presentation, slides 14–17. Those observations motivate the survey; they are not a statistical measurement of every country’s graduates.

The pipeline that is not a CPU

A five-stage RISC-V exercise teaches dependencies, forwarding and control hazards. A packet processor or video filter also needs a different set of decisions: where results wait, how stalls propagate and how much work is already in flight. A FIFO can absorb a burst, but finite storage cannot solve a sustained throughput mismatch.

One useful assignment is an arithmetic pipeline with a FIFO at its output. Randomly stop the receiver. Require the student to preserve order, prevent overflow and explain when the input must stop. Then replace local backpressure with credits and ask what the credit counter represents. These are concrete, checkable skills.

MIET’s public practical course explicitly includes arithmetic pipelines, systolic arrays, ready/valid, credit flow control and CDC. The distinction matters: our item 1.1 counts non-CPU pipelining; a CPU pipeline earns a different point.

A waveform is not a verification strategy

A testbench should say what is correct, not merely draw what happened. A transaction model describes expected behavior at the appropriate abstraction. Drivers create bus activity; passive monitors observe it; a scoreboard reconciles observations with expectations.

Randomization is useful when its constraints produce meaningful traffic and its coverage model identifies which situations were exercised. Functional coverage is not code coverage. A passing directed example cannot establish that reset during a transfer, simultaneous queue events or long downstream stalls have been handled.

Concurrent assertions add temporal rules to simulation. Formal checking can examine a small block under explicit assumptions without enumerating simulation tests. These receive separate points. So do UVM, commercial hardware emulation and differential checking of processor RTL against an instruction-set simulator.

Berkeley’s ASIC verification lab names UVM, coverage and formal techniques. MIT’s cocotb-oriented coverage material provides another route. Under the requested convention, a documented UVM course receives 3.2–3.5 plus its own UVM point; the report exposes that convention instead of presenting all five as independently checked assignments.

Make the physical consequences visible

Students should take an RTL block into an ASIC flow and read a timing report. Where is the critical path? What is the required time? Which change addresses the cause of negative slack? A smaller clock frequency requirement can make a report green while leaving the original specification unmet.

Power needs the same discipline. A register enable, a latch-based integrated clock-gating cell and a switched power supply are different mechanisms. An enable may stop data updates while the clock still switches. The netlist and reports should reveal what the tool actually implemented.

ETH’s open ASIC exercises and Cambridge’s current 4B28 coursework show two teaching routes. The rubric accepts documented open and commercial flows, but an FPGA timing report does not earn the ASIC STA-lab point.

A project path for a meetup or seminar

  1. Build and simulate a small digital system.
  2. Add a non-CPU pipeline, finite queues and randomized backpressure.
  3. Write a reference model and automatic transaction checks.
  4. Use functional coverage and temporal assertions; formally check a small block.
  5. Handle a clock-domain boundary deliberately.
  6. Read ASIC timing and power reports, then justify an improvement.
  7. Keep the specification, code, tests and reports as a reviewable project.

The Basics, Graphics and Music repository can support the first steps with visible graphics and sound on FPGA boards. The advanced tasks should then make flow control and verification explicit. A demonstration that looks right is useful feedback, but it should be accompanied by repeatable checks.

Basics, Graphics and Music (BGM)

The 49-item rubric gives one point per documented topic across microarchitecture, clocks/memory/gating, verification, ASIC implementation, processor RTL, applications and EDA software. A question mark means unverified, not absent. Scores describe the inspected public evidence, not the quality of a university or its graduates.

For a student, the useful question is “Which assignment will let me demonstrate the next skill?” For an instructor, it is “What artifact would convince someone that this topic was learned?” Publishing lab specifications and examples would improve both the curriculum comparison and the student’s ability to choose a course.
