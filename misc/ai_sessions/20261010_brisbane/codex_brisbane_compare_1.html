Brisbane BRS-100: Codex and Claude board-support comparison

Codex has the stronger checked LCD timing and electrical configuration; Claude offers better physical connector-orientation guidance and includes the normal Gowin GUI project files. Neither implementation has been demonstrated on the assembled board. The most urgent issues are the inherited LCD raster errors, the 1.8 V defaults in Claude’s alternate constraints, and the need to verify the exact FPGA target and actual display/module combination.

Both worktrees are clean. On resumption, all files in the earlier evidence manifest still matched their hashes. See the snapshot manifest and resumption checks.

Each implementation supplies 480×272 and 800×480 configurations, each with a manufacturer-GPIO version and an _alt version with peripheral-named ports. The scope is the requested first LCD + TM1638 pair, with optional microphone and DAC. Separate no-TM1638, HDMI and dedicated sound-only variants remain possible later work, not functionality added by this comparison.

The report uses saved source snapshots and completed review builds from 11 October, plus a new isolated simulation probe on 12 October. Advantages and disadvantages

Codex advantages: measured active-area correctness, an explicit RGB-to-clock timing scheme, panel output constraints, controlled reset, defined disabled-interface behavior, documented electrical differences from the vendor file, and reproducible pin/raster tests. Its grouping leaves one more spare GPIO and reduces the mental effort of wiring the color bus.

Codex disadvantages: more custom RTL and duplicated files to maintain; a different lab clock at 800×480; timing profiles that still need to be matched to an exact panel; an exact-device build dependency that blocks the installed Education package; and no ready-to-use 05 GUI path. The README is thorough but long, and the TM1638 translator remains a proposed circuit rather than a validated module assembly.

Claude advantages: recognizable Tang Nano structure, less new raster code, consistent lab clock, ready GUI assets, smaller documentation for the 800 variant, and excellent physical orientation guidance. Preserving vendor constraint statements verbatim makes upstream comparison straightforward.

Claude disadvantages: reuse carries existing raster defects into this board; source compatibility has been favored over connector grouping; alternate electrical constraints are incomplete; global warning suppression weakens checking; reset and registered-graphics clock crossings need attention; and several power/device claims are stronger than the evidence.

Errors, risks and unresolved questions

1. Claude’s reused LCD controllers generate an incorrect active area

Confirmed RTL defect. The 480 controller uses inclusive upper bounds for active coordinates, producing 481 pixels on 273 active lines. Its VSYNC expression never becomes high during a frame. The 800 controller produces 801 active pixels per line. These defects are inherited from shared BGM peripherals, not newly invented in the Brisbane wrapper, but they are present in the resulting support package. See 480 controller, 800 controller and the measurements below.

A DE-only panel might ignore VSYNC or tolerate part of this behavior; that does not make the programmed active dimensions correct. Fix interval endpoints and frame wrap, then validate exactly one complete frame including blanking and all four edges. Do not assume a color-bar picture proves all timing is correct.

2. Claude’s alternate CST omits electrical I/O declarations

Confirmed constraint problem. The 480 alternate CST contains IO_LOC statements but no IO_PORT statements. The compiled pin report identifies LCD outputs, MIC_SD and TM1638 DIO as LVCMOS18. The board’s expansion banks operate at 3.3 V. This is a mismatch between the design’s electrical declaration and the intended interface, not evidence that the tool changes the physical supply voltage.

Specify LVCMOS33 for the expansion/clock/UART signals and LVCMOS18 for the separate button/LED bank, then choose pulls and drive strengths per direction. The same missing declarations exist in the 800 alternate CST; the concrete compiled evidence here is the 480 alternate build. Claude’s main manufacturer-based CST already specifies LVCMOS33 for the headers. Do not generalize the alternate’s fault to all four Claude configurations.

3. Keeping every vendor electrical setting creates a build-policy inconsistency

Confirmed build discrepancy. Claude keeps DRIVE=8 on the microphone input and uses set_option -cst_warn_to_error 0 in batch Tcl. Its GUI configuration instead sets Promote_Physical_Constraint_Warning_to_Error to true. A batch probe with that stricter policy fails on CT1108 for pad_io[13]; see the log.

This is evidence for a CLI/GUI policy conflict, not a claim that the GUI itself was launched and tested. Global demotion can also hide misspelled constraints. Codex makes small documented electrical edits while preserving every location. That is the preferable compromise for this repository’s philosophy. If exact vendor-file identity is required, design and test a narrowly scoped overlay instead of disabling a whole class of errors.

4. Claude’s 800×480 path is not a general solution for registered graphics

Confirmed timing failure in one lab; architectural limitation. The pixel coordinates run at 32.4 MHz while the lab runs at 27 MHz. A lab with registered RGB cannot supply a newly computed value for every pixel at the faster rate without a buffering or scheduling scheme. The wrapper does not provide one. In the reviewed 3_11_microphone_monitor build, the timing report lists 33 setup-violated endpoints.

This does not contradict Claude’s narrower claim that its simpler oscilloscope lab passed with a different tool version. It does disprove treating that one result as evidence for all Tang Nano-equivalent labs. Also, the Claude SDC has no LCD data/control output delays, so internal timing success alone cannot establish panel setup/hold. Codex’s single 31 MHz domain at 800×480 avoids this rate mismatch, but it changes the lab clock and only supports the documented RGB pipeline depth.

5. TM1638 and DAC power instructions need module-specific validation

Electrical recommendation needs correction. Claude tells students to power any TM1638 module from 3.3 V. This avoids a 5 V DIO signal at the FPGA, but operation at 3.3 V is not established by the referenced Titan Micro datasheet, page 15, whose electrical specifications use 4.5–5.5 V. Treat 3.3 V operation as requiring evidence for the exact module rather than as a universal solution.

Codex proposes 5 V power and a bidirectional TXS0104E translator, including separate supplies and common ground. This is more explicit, but the exact translator module, pull resistors, load capacitance, DIO turnaround and waveform quality still require validation; TI’s device documentation does not validate an arbitrary breadboard assembly.

Claude’s diagram also sends 3.3 V to PCM5102 VIN. That is correct only for a compatible module power circuit; a VIN pin feeding an onboard regulator may need a different supply. Codex correctly distinguishes regulated 5 V modules from 3.3 V-only boards. Neither report establishes which physical module the student owns.

6. The exact FPGA part remains an acceptance gate for both sides

Unresolved device-model compatibility. Both identify the manufacturer part as GW1NR-LV9QN88PC7/I6. Codex selects it and fails early with the installed device database. Claude substitutes GW1NR-LV9QN88PC6/I5 and describes timing as pessimistic. Shared device family and programmer ID do not alone establish the suitability of the substitute speed/temperature model or bitstream for the actual part.

Use an exact-target build as the release criterion, or obtain and record explicit manufacturer/Gowin guidance for the fallback. Codex’s temporary C6/I5 builds are useful implementation probes, not validated C7/I6 binaries. Claude’s default substitution is disclosed in the README and Tcl, but should also be obvious in the user’s build output. See the manufacturer reference project.

7. Reset, disabled interfaces and simulation compatibility

Codex gates reset with PLL lock and synchronizes release; Claude uses the existing power-up pulse and raw buttons without incorporating PLL lock. This is a startup robustness concern that needs power-cycle and button testing, not a measured board failure. With graphics/microphone disabled, the wrapper probe observes zero coordinates and microphone data in Codex, while Claude leaves those lab inputs undriven. Defined inactive inputs make labs easier to simulate and debug.

The initial no-TM1638 probe also showed high-impedance Claude LEDs. An isolated reproduction traced this to the shared SWAP_BITS macro’s $bits-based generate bound under Icarus 12: the macro yielded zzzzzz, while a constant-bound equivalent yielded 011111. See the isolated probe. Classify this as a reproducible simulator/construct compatibility issue. It is not proof that Gowin produces undriven LEDs in hardware, and it is not unique to Brisbane.

8. Two documentation promises need narrower wording

Claude says grounding the microphone’s L/R pin lets J5.12 be left free. It can be left physically unconnected, but the RTL still drives that pin low through the microphone controller, and the lab GPIO bus still has only two bits. Reclaiming it as a third lab GPIO requires HDL changes.

Codex openly documents its missing Gowin GUI fragments. That honesty is useful, but the omission remains a functional gap compared with the normal Tang Nano workflow: 05_run_gui_for_fpga_synthesis.bash is not supplied with the board-specific project pieces it expects. Adopt Claude’s GUI integration, after aligning its constraints and target with the batch flow.

The two wiring plans are different. Selecting a different resolution within one author’s pair does not require rewiring, and main/alternate versions within that pair retain the same connections. Both main configurations preserve all 47 manufacturer IO_LOC assignments and declare the 32 header GPIOs as inouts. The peripheral mapping therefore belongs in the wrapper, as requested. An inout declaration does not make an input-only microphone data wire safe to drive, nor does it remove the need for direction-appropriate electrical settings.

Both documentation sets correctly distinguish FPGA package numbers from connector positions, identify J5.18 as 5 V and J6.18 as 3.3 V, and explain that the adapter’s 30-pin header is not a standard 12-pin Pmod. Both warn to open the adapter color-shortening solder bridges. These are important strengths. The manufacturer pinout and adapter schematic/PCB drawing remain the reference for assembly.

Documentation quality and claims to keep precise

  • Codex: strongest explanation of panel compatibility, FPC contact orientation, power sequencing, current budget, translator wiring and actual test limits. Its preserved vendor file and electrical-change list make review easy. The README should begin with a shorter bill of materials and bring-up checklist; exact panel/module part numbers would be more useful than several conditional power instructions.
  • Claude: shorter narrative and readable header tables. The 800 README sensibly reuses common wiring instructions. However, “same design,” “same die” and a few successful labs should not imply universal compatibility. Describe what was measured and what remains assumed.
  • Both: distinguish resolution from a validated panel model. In particular, a “usual 40-pin RGB connector” is not a compatibility guarantee. Confirm voltages, FPC contact side, DISP/backlight behavior, sampling edge, porches and setup/hold against the actual panel.
  • LED order: a TM-enabled one-hot probe maps lab bit 0 to manufacturer LED1 in Codex and LED6 in Claude. This is a convention difference, not automatically a defect. Document the bit order explicitly and verify silkscreen labels on hardware; the manufacturer pinout and schematic use differing naming conventions.
  • GUI and packaging: Claude’s sibling include reduces duplicated HDL but means the 800 directory is not self-contained. Codex duplicates most support files, which is portable but invites drift. Test exported exercise packages and include dependencies before presenting either as a self-contained board package.
  • Programmer identity: Codex uses brs-100-gw1nr9; Claude uses tangnano9k. In the checked openFPGALoader board table, both use the same FT2232 cable settings, with the BRS entry adding its part string. Therefore the Tang Nano name is misleading but is not a demonstrated programming failure. Prefer the BRS name when the installed version lists it; check actual USB behavior.

Recommended order of work

  1. Choose the physical assembly. Record board revision, both panel model numbers, PMOD-RGBLCD revision, TM1638 module, translator and DAC supply circuit. Establish one wiring plan per selectable configuration.
  2. Correct Claude’s immediate defects. Fix active-area bounds and VSYNC; add alternate electrical constraints; remove input-only DRIVE settings or apply a verified narrow override; align GUI and batch policies.
  3. Resolve exact-target tool support. Build C7/I6 with an appropriate database, or document vendor-supported fallback instructions. Do not distribute the temporary comparison bitstreams as board-ready results.
  4. Settle the 800 graphics clock contract. Use a consistent lab/pixel clock or a deliberate buffering scheme. Test both combinational and registered RGB, including the microphone-monitor lab. Review output delays and unconstrained paths.
  5. Complete Codex’s GUI support and reduce drift. Generate GUI assets from the same target/options as the batch flow. Share stable board logic without breaking standalone/exported exercise packages.
  6. Bring up hardware in stages. Check unpowered continuity and rails; start with onboard LEDs/UART; then static RGB and panel-edge patterns; then TM1638 through the selected level circuit; finally microphone/DAC together. Measure pixel and serial waveforms at the module connectors.
  7. Run regression and startup checks. Both resolutions, main/alternate mappings, all feature combinations and no-TM macro; walking-one pin checks; bidirectional DIO release; repeated power cycles and button resets. Investigate the shared SWAP_BITS/Icarus issue independently.
  8. Extend the family after the first pair works. Add dedicated no-TM1638, sound-only or HDMI variants only with complete pin/power documentation and checks. Existing spare-pin counts mean LCD + TM1638 + microphone + DAC is possible in both current mappings; a sound-only variant is not forced by GPIO shortage.

The comparison task is complete. This report identifies concrete follow-up work; it does not claim that the recommended fixes, exact-target implementation or hardware validation have already been completed. No BSP source was changed during the comparison.
