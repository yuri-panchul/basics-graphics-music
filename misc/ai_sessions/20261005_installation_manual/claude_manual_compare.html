BGM installation manual · version 0.2 · two editions

They read the RTL. I read the Word file.

Both editions added the UART terminal chapter from the same terminal_installation.docx. Codex also opened the three exercises' SystemVerilog and found that the document's advice is wrong for one of them — and that two of my descriptions of what the board does were wrong. I have checked every claim against the source and fixed my manual.

Verdict: they win this round on the facts

Codex's terminal chapter is grounded in the exercises' RTL; mine was grounded in the supplied document. Where the two disagree, the RTL decides, and it decided against me three times out of three: what the seven-segment exercise actually displays, where the calculator puts its answer, and whether a line ends with CR only. On top of that they caught a usability trap I walked straight into — turning local echo on unconditionally, which breaks the echo exercise.

All of it is now corrected in my 0.2. What I keep over theirs is the figure coverage (127 cropped screenshots against 75), the errata in three languages rather than one, and a terminal chapter that sits inside each operating system's own walk-through instead of in a separate chapter.

8_1_1 "shows the code of the received byte on the seven-segment display" The display shows rx_buf[i] - 8'h41 + 8'hA, so only capital A…F map to hex digits A…F; 0…9 come out as nonsense. The low-nibble line that would have made digits work is in the source, commented out. 8_1_1/lab_top.sv
8_1_3 "you type an expression and get the answer", implying the terminal The answer goes to the seven-segment display, in hex: display_number <= res_data, and uart_tx = '1 — the transmitter is off in this exercise too, so the terminal never receives anything. 8_1_3/lab_top.sv:69,223
"the end of an expression is a carriage return" Either one: (fifo_data_i == cr) | (fifo_data_i == "\n"). And a terminal that sends CR+LF can have the expression read as two ends of line. 8_1_3/ascii2tok.sv:51
"turn local echo on so the characters are visible", as a permanent ~/.minirc.dfl setting Right for 8_1_1 and 8_1_3, wrong for 8_1_2: that exercise echoes in hardware, so local echo doubles every character and the test proves nothing. Codex spells out the setting per exercise and says outright that they are correcting the DOCX. 8_1_2/lab_top.sv
"UART is a serial channel carried by the same USB cable the board is plugged in with" True for FTDI-based boards, false for a board programmed by a separate JTAG programmer such as a USB Blaster, which provides no serial port at all. Codex requires the board's own UART or a USB-to-UART adapter, with TX/RX/GND wiring. board documentation
Nothing said about where 14_run_terminal_program.bash exists It is present only in 8_1_1_uart_7segment. For the other two the terminal has to be opened by hand. 8_1_uart/*/
"look for /dev/ttyUSB* or /dev/ttyACM*", then use the helper script The helper globs /dev/tty${tty_suffix}* with the suffix fixed per platform: USB on Linux, S under Git Bash, .usbserial- on macOS. An ACM device is invisible to it and must be opened manually. It also always starts picocom with --echo — which is exactly wrong for the echo exercise. 00_setup_terminal.source_bash:36-57,209
macOS: picocom … /dev/tty.usbserial-0001 For your own connections the right device is /dev/cu.*; /dev/tty.* waits for a DCD signal and can hang on open. Codex says cu. macOS serial convention
PuTTY from putty.org.ru/download, because the DOCX shows that page A third-party mirror. Codex keeps the screenshot as a historical source and points the live link at the developer's own download page. Better advice: signed installer, current version. —

What I am adopting

  1. Already done: the ten factual corrections in the table above, in all three languages.
  2. The repository's Vivado Linux screenshots. Eight PNGs sitting in docs/vivado_installation_guide/, plus board_sel.png and license.png, would turn my Vivado sections from prose into a walk-through. There is no reason I linked to them instead of using them.
  3. A landing page. Three languages, the errata, and a line saying what the edition is.
  4. A SHA-256 manifest and a validation script in the package. I run the structural checks by hand each time; theirs is committed and repeatable, which is the better habit.
  5. Per-symptom troubleshooting. My FAQ gained three UART questions; their 4.4.6 is better organised and worth copying in shape.

Recommendations for their edition

  1. Translate the change log. changes.html is Russian only, while the manual is in three languages. An English reader is told the manual was audited but cannot read the audit.
  2. Link the audit to the manual. Their change log names sections in prose; 70 deep links per language make an errata usable as a to-do list rather than a report.
  3. Use the finer crops. 64 figures from a 68-page manual means roughly one per page; the original has several dialogs per page. The board-and-JTAG photographs and the Programmer "Successful" screenshots are missing altogether, and those are exactly the two places a beginner gets stuck.
  4. Add the repository's own Windows port helpers. check_which_port_is_used.bat and drive_uart.bat live in the exercise directory and answer "which COM port is it" without Device Manager. Neither is mentioned.
  5. Reconsider the single terminal chapter. Writing it once avoids triplication, but a Windows reader working through 4.1 now has to jump to 4.4 and find the Windows parts of it. A short per-OS pointer with the commands, and the shared material in 4.4, would serve both.
  6. Keep the wirenboard and picocom manual links. The DOCX gave a Russian minicom guide; they replaced it with the Debian packaged manual. For the School's audience the Russian walk-through is the more useful of the two — keep both.

The lesson I am taking from this

I treated terminal_installation.docx as the specification and the repository as background. Codex treated the repository as the specification and the document as a draft to be checked against it — and said so in the text, which is why their manual contains sentences like "the DOCX instruction to always enable echo is refined here according to the exercises' behaviour".

Everything I got wrong came from that one choice. The supplied document was written before the exercises settled; three of its statements, and four of mine that followed from it, do not match the RTL that ships today. When a document and the code disagree, the code is what the student will run.
