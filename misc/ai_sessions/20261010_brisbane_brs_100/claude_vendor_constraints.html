Vendor constraints, pin mapping in RTL

Branch claude_brisbane_brs_100 · 10 October 2026 · Claude Opus 5.5

The repository keeps each board's constraint file as the manufacturer wrote it and does the peripheral wiring in board_specific_top.sv. The BRS-100 now has one configuration of each kind, with identical jumper wiring, which makes the trade-off measurable instead of hypothetical.

Verdict. The vendor-file approach is the right default here, and brisbane_brs_100_tm1638_pmod_rgblcd_by_claude should be the configuration the later variants build on. It cost one tool setting, four unused port declarations and one SDC change; in return it fixed an I/O standard that the hand-written file had left at a 1.8 V default on 3.3 V banks.

The two configurations

_alt — mapping in the .cst

IO_LOC "MIC_SD"     39;  # J5.13
IO_LOC "LCD_R[3]"   75;  # J6.3  J2.30 R0

// board_specific_top.sv
input  MIC_SD,
output [7:3] LCD_R,

primary — vendor .cst, mapping in RTL

IO_LOC  "pad_io[13]"  39;
IO_PORT "pad_io[13]"  IO_TYPE=LVCMOS33
                      PULL_MODE=DOWN DRIVE=8;

// board_specific_top.sv
inout  [32:1] pad_io,
.sd ( pad_io [13] ),            // J5.13
assign pad_io [19] = LCD_R [3]; // J6.3

The primary configuration's board_specific.cst is location.cst from BrisbaneSilicon's repository at commit cd0bcbf1, byte for byte, under a provenance comment.

Advantages

  • Proseen hereThe electrical settings come with the pins. The vendor file sets IO_TYPE=LVCMOS33 on the 3.3 V banks. The hand-written _alt file only placed pins, and Gowin fell back to LVCMOS18 with pull-ups. The build of tang_nano_9k_lcd_480_272_tm1638 reports the same. Nobody chose that; it happened by omission.
  • ProOne constraint file per board, many configurations. The planned _no_tm1638 and _tm1638_no_graphics_but_sound variants change only board_specific_top.sv, or a two-line wrapper of it. With function-named constraints each variant would carry its own diverging .cst.
  • ProDiffable against the source. When BrisbaneSilicon updates location.cst, the update is a file copy and a readable diff. A hand-edited file has to be re-derived and re-checked pin by pin.
  • ProNames match the board documentation. pad_io[13] is pin 13 of J5 in the vendor's pinout PDF, schematic and example project. A student moving between the manual and the code needs no translation table.
  • ProThe wiring decision is in reviewable RTL. Which header pin carries which signal sits in one block of assigns with comments, next to the modules it feeds, where it can be read, simulated and changed.
  • ProIt is how the rest of the repository works. Tang Nano 9K keeps Sipeed's names and wires the INMP441 L/R line to TF_CS in the top module; de10_lite keeps Terasic's GPIO[0] and comments it // JP1 pin 1; the Arty boards keep Digilent's master XDC with ja[0]. A board that breaks the pattern is harder to maintain beside them.

Disadvantages

  • Conseen hereThe vendor file can conflict with the tool flow. It puts DRIVE=8 on every header pin. Gowin rejects drive strength on a pin the design uses only as an input — pad_io[13], the microphone data — with CT1108, and this repository's flow treats constraint warnings as errors. The fix chosen, set_option -cst_warn_to_error 0, also turns a mistyped port name in any constraint into a warning. The alternative, assign pad_io[13] = 1'bz;, works too but does not cover a lab that only reads its GPIO.
  • Conseen hereEvery constrained port must exist. The four SPI flash pads are declared as inout ports the labs never use, only so the constraints have something to bind to. They add four warnings to every build.
  • Conseen hereTiming constraints lose their meaningful names. The pixel clock is now constrained as [get_ports {pad_io[9]}]. Constraining the internal net failed (TA2003, the net is renamed in synthesis), and a PLL-pin constraint would fail in labs without graphics, where there is no PLL.
  • ConIndex arithmetic replaces names. J6 pin 3 is pad_io[19]; the vendor counts from 1; the Tang-compatible LED order reverses pad_leds_n[6:1]. Each is a place to be off by one or reversed, and the tools cannot catch it — a wrong index still builds.
  • ConDirection checks disappear. With every header pin an inout, connecting an output to an output, or forgetting to drive a pin, produces no port-direction error. Reports and pin tables say pad_io[24] rather than LCD_G[2], so reading them needs the README.
  • ConThe vendor's electrical choices may not fit the peripheral. Every header pin gets a pull-down. That is harmless for the LCD and I2S lines, but the TM1638 data line is usually pulled up by a resistor on the module, and the FPGA's weak pull-down works against it. This should be checked on hardware.
  • ConSome interfaces cannot stay inside the vendor file. Differential outputs are constrained as pairs, as in tang_primer_25k_pmod_hdmi: IO_LOC "TMDS_0_CLK_P" H5,J5;. A PMOD-HDMI variant of the BRS-100 would have to replace the single-ended pad_io lines for those pins, so the file would no longer be the vendor's.

Where the rule should bend

Keeping the vendor file is a default, not an absolute. It should give way when:

  • the interface needs constraints the vendor file cannot express, such as differential pairs or another I/O standard on a bank;
  • the vendor file is wrong for the board. Fix it then in a separate, labelled block below the untouched original, never by editing lines in place, so the diff stays readable;
  • the vendor file conflicts with the flow, as with CT1108. Prefer a flow setting scoped to the board, in board_specific.tcl, over editing the file.

Recommendations

  1. Build the next BRS-100 variants on brisbane_brs_100_tm1638_pmod_rgblcd_by_claude: _no_tm1638 as a two-line wrapper, and the sound-only variant as another top module over the same board_specific.cst.
  2. Keep _alt for now as the reference that shows the same wiring with named constraints; remove it once the primary has been tried on a real board.
  3. Try both configurations on hardware once: LCD image, TM1638 keys with the pull-down, microphone level and DAC output. Nothing here has run on a board yet.
  4. Consider adding IO_TYPE=LVCMOS33 to the Tang Nano 9K constraints. The LVCMOS18 default on its 3.3 V banks is the same omission found in _alt.
