ALINX AX7035B · HDMI output · post-mortem

Why the HDMI Stayed Dark

Two implementations of HDMI output for the same board. One drives a monitor, one does not. This is what separates them, starting with the single line that accounts for it.

working codex 4b2fe932 dark claude 7de707c8 part xc7a35tfgg484-2 analysed 2026-10-04
Root cause

Pin M6 switches the connector's +5 V supply, and it is active high

My code drives it low to enable, inferring active-low from the N at the end of the inherited signal name HDMI_OEN. So on my bitstream the HDMI connector never receives power: the monitor sees no hot-plug voltage and reports no signal, regardless of what the three data lanes are transmitting.

The polarity is documented in the ALINX AX7035B user manual, HDMI section, which the codex implementation cites and follows — its comment reads “M6 controls HDMI1's +5 V supply and is active high, despite OEN's name.” I flagged the polarity as a guess in my commit message and in my hand-off notes. Flagging it was honest; it was not a substitute for reading the manual, which was available.

My non-graphics branch has the same error with the opposite sign: it drives M6 high while transmitting nothing, powering the connector for a design that has no video to send.

claude — wrong both ways 
// graphics on
localparam hdmi_output_enable = 1'b0;
assign HDMI_OEN = hdmi_output_enable;

// graphics off
assign HDMI_OEN = ~ hdmi_output_enable;
codex — follows the manual 
// graphics on, after reset releases
assign hdmi_enable = ~ pixel_rst;

// graphics off
assign HDMI_OEN = '0;

The pin question, settled by measurement

Codex constrains all eight TMDS pins explicitly, citing the manual. I constrained only the four positive pins and let Vivado derive each partner. That looked like a candidate cause, so I placed my design and asked what it had actually chosen: 

PINCHECK TMDS_clk_p     -> E1      PINCHECK TMDS_clk_n     -> D1
PINCHECK TMDS_data_p[0] -> G1      PINCHECK TMDS_data_n[0] -> F1
PINCHECK TMDS_data_p[1] -> H2      PINCHECK TMDS_data_n[1] -> G2
PINCHECK TMDS_data_p[2] -> K1      PINCHECK TMDS_data_n[2] -> J1
PINCHECK HDMI_OEN       -> M6

identical to the codex constraints, pin for pin

So that difference is cosmetic. Being explicit is still better — it documents the intent and survives a tool that changes its inference — but it is not why the screen is dark. Ruling it out mattered: it was the difference most likely to be mistaken for the cause.

Reset release into the serializer

A 10:1 DDR serializer on Artix-7 is a pair of OSERDESE2 primitives joined by a shift chain. Both have to leave reset on the same CLKDIV edge, or the pair starts out of step and the ten bits of each symbol are framed wrongly. The reset therefore has to be released synchronously.

claude — combinational, no synchroniser 
wire rst = ~ rst_n | ~ mmcm_locked;

// straight into OSERDESE2.RST,
// the encoders and vga
codex — async assert, sync release 
wire reset_request = rst_in | ~ locked;

(* ASYNC_REG = "TRUE" *)
logic [2:0] video_reset = '1;

always_ff @(posedge pixel_clk or
            posedge reset_request)
  if (reset_request) video_reset <= '1;
  else video_reset <= {video_reset[1:0], 1'b0};

I call this a probable fault rather than a confirmed one because the power rail alone fully explains a blank screen, so it has not been observed. It would produce a different symptom — a monitor that syncs and shows noise or a torn image — and it should be fixed whether or not it has bitten yet.

Duplicated code the repository already had

peripherals/dvi.sv has been on main since a commit titled “Fix quartus synth error”, and provides dvi_sync, tmds_encoder and a generic serializer. Everything in peripherals/ is compiled for every board by the Vivado script, so it was available to me the whole time. Codex used it. I copied svo_tmds.v out of boards/marsohod3gw2/ instead, adding a fourth copy of a TMDS encoder to the tree.

The cause is unglamorous. I did search for the existing encoders, and truncated the result:

Why my verification did not catch it

I proved the design builds. Codex proved the design works.

My evidence was implementation evidence: timing met with 22.8 ns of slack, zero DRC violations, 8 OSERDESE2 and 4 OBUFDS placed, a bitstream written, both branches of the conditional compiled. Every one of those checks passes with the power-enable pin inverted, because none of them looks at what the pins mean.

Codex wrote a self-checking testbench that instantiates AMD's own MMCM, serializer and output-buffer models, decodes the differential output, and verifies every pixel and blanking symbol of a complete frame, then repeats after an asynchronous reset. And for the facts a simulation cannot supply — which pin, which polarity — it went to the vendor manual rather than to the signal's name.

Only the last two rows would have found it, and only one of them is engineering rather than paperwork. A simulation however thorough cannot tell you that a pin called OEN is active high; the testbench verifies the lanes it is given, not the rail that powers the connector. The finding is specific: for a signal whose behaviour lives in the hardware rather than in the RTL, a documented source is the only verification that counts — and naming conventions are not a source.

Fixing my implementation

  1. Invert the power enable: drive M6 high to enable, low when idle. One localparam and the inverted use in the non-graphics branch.
  2. Add per-domain reset synchronisers with async assert and synchronous release, feeding OSERDESE2.RST and the encoders, plus set_false_path -from [get_ports rst_n].
  3. Replace the copied svo_tmds.v with the shared dvi_sync and tmds_encoder from peripherals/dvi.sv, and delete the duplicate.
  4. Match the clock lane symbol to the data lanes rather than inverting it.
  5. Constrain all eight TMDS pins explicitly, citing the manual section, even though Vivado infers the same four.

Items 1 to 3 are corrections. Items 4 and 5 bring the implementation in line with a reference that is known to work, which is worth more than my judgement about whether a sink tolerates an inverted clock.

The honest summary of the comparison is shorter than the comparison: on this task codex produced the better implementation. It sourced the hardware facts from the vendor, verified behaviour rather than buildability, reused the repository's own modules, and documented both the result and the limits of its testing. Mine built cleanly and did not work.
