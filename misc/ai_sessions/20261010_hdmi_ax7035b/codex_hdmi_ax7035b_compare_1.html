Conclusion

Both implementations produce working simulated TMDS video for a combinational RGB source, and both complete a fresh color-stripes build through bitstream generation. Codex preserves the 50 MHz lab clock and has stronger checked-in tests. Claude uses a simpler 25 MHz lab/pixel clock arrangement and fewer resources. Neither implementation handles arbitrary registered RGB pipelines correctly.

Recommended direction: keep the vendor XDC with HDMI lines uncommented and the requested reset false path; retain 50 MHz as the compatibility default; define and test the RGB latency contract before combining code. Adopt Claude’s module separation and Codex’s reproducible verification.

This is a source comparison with fresh simulation and implementation evidence, not a claim of HDMI compliance or a newly observed picture on a physical monitor. No FPGA was programmed during this review.

How each implementation works

Codex: keep the lab at 50 MHz

  1. The board’s 50 MHz oscillator enters one MMCM. It generates related 50 MHz lab, 25 MHz pixel, and 125 MHz serializer clocks.
  2. Reset asserts on the button or loss of MMCM lock. Separate three-register chains release the lab and pixel resets in their own clock domains.
  3. The shared dvi_sync counts the 800 × 525 frame and provides 640 × 480 visible coordinates.
  4. The lab uses the coordinates to produce RGB. It receives two clock cycles per pixel. The HDMI module samples RGB and its corresponding sync/visible signals together at 25 MHz.
  5. Three common TMDS encoders convert the colors into ten-bit symbols. Each data channel and the clock channel uses an OSERDESE2 master/slave pair and an OBUFDS differential buffer.
  6. HDMI1’s power-enable pin goes high after pixel reset releases. With graphics disabled, the lab uses the original oscillator, coordinates are zero, and HDMI power is off.

Codex: ax7035b_hdmi.sv:26 · Codex: board_specific_top.sv:156

Claude: run the lab with the pixels

  1. hdmi_clk_gen derives 25 MHz pixels and a related 125 MHz serializer clock from the board’s 50 MHz oscillator.
  2. One three-register reset synchronizer serves both the lab and video because both run at 25 MHz.
  3. The existing vga module generates the same default frame dimensions, sync pulses, and visible region.
  4. The lab generates RGB on the pixel clock. hdmi_tx feeds RGB and the current sync/visible signals directly into the shared TMDS encoders, without compensating for registered lab output.
  5. Four serializer pairs and differential buffers emit the same type of video-only TMDS signal through HDMI1.
  6. HDMI power follows reset. With graphics disabled, the lab returns to 50 MHz and HDMI power is off, but x and y have no drivers.

Claude: hdmi_clk_gen.sv:29 · Claude: board_specific_top.sv:79 · Claude: hdmi_tx.sv:65

Both defaults use 25 MHz pixels, 800 × 525 total pixels, approximately 59.52 Hz, and 250 Mbit/s per data lane. Both provide DVI-compatible video through the HDMI connector, with no audio, EDID/DDC negotiation, hot-plug handling, or HDCP logic. The pixel clock is below the nominal 25.175 MHz 640 × 480 VGA clock; test monitor compatibility rather than assuming every display accepts it.

Bugs, limitations, and evidence

Confirmed conditional failure · both

F1. RGB pipeline latency is not handled generally

Claude’s encoder sees current sync/visible signals with the previous pixel’s registered colors when the lab uses one register stage. Codex’s faster lab clock accommodates one stage in the focused test, but a two-stage pipeline still presents stale color data at the sampling edge. Both two-stage cases fail at the first pixel of row 1.

This is a compatibility issue for registered graphics sources, not a failure of the passing combinational color-stripes design. The repository contains registered graphics paths: game_sprite_display registers sprite output and game_mixer registers the final color. The optional pipelined sprite adds more latency. Their actual images and edge pixels still need direct end-to-end tests.

Fix direction: specify the lab’s RGB latency, align sync and data-enable with that delayed RGB, and check line/frame boundaries. Adding an equal register to both RGB and controls does not correct an existing latency mismatch. Do not blindly add the same delay to every lab; that would shift combinational labs.

Codex: ax7035b_hdmi.sv:85 · Claude: hdmi_tx.sv:93 · Codex: game_sprite_display.sv:140 · Codex: game_mixer.sv:22.

Confirmed simulation defect · Claude

F2. Graphics-disabled x and y are undriven

The no-graphics branch disables HDMI correctly but never assigns x and y. The focused test observes zzz. Labs that ignore those inputs are unaffected; other logic may propagate unknown values in simulation, while synthesis can optimize unconnected inputs differently.

Fix: add assign x = '0; and assign y = '0;, following Codex. Claude: board_specific_top.sv:252 · Codex: board_specific_top.sv:179.

Supported-mode limitation · both

F3. Exposed parameters promise more flexibility than the full path implements

Codex hard-codes the MMCM ratios, coordinate widths and eight-bit RGB interface; the wrapper’s pixel_mhz and screen parameters do not reconfigure the transmitter. Its README discloses the fixed mode, but there is no elaboration guard against incompatible overrides. Changing clk_mhz can also make lab timing parameters disagree with the actual generated clock.

Claude forwards clock parameters to its helper, but rounds the pixel-clock divider to an integer and does not validate legal MMCM ranges or the exact 5:1 clock ratio. It leaves VGA dimensions at their defaults and also presents eight-bit color ports. Frequency parameterization alone is not complete video-mode support.

Recommendation: assert the supported defaults, or implement a small validated mode table that updates clocks, timing, widths and tests together. This is not a demonstrated failure at the defaults. Codex: ax7035b_hdmi.sv:26 · Claude: hdmi_clk_gen.sv:47 · Claude: board_specific_top.sv:211.

Shared timing review item

F4. The reset false path also applies without graphics

Both files contain the requested broad exception from rst_n. Graphics mode synchronizes reset release; non-graphics mode passes ~rst_n straight to the lab. The exception suppresses external-reset timing paths but does not itself make reset release safe in every downstream lab.

Keep the requested constraint. Document its scope and evaluate synchronized reset release for non-graphics mode in a separate change. This is a shared design concern, not a newly reproduced hardware failure. Codex: board_specific.xdc:16 · Claude: board_specific_top.sv:108. AMD describes the timing-analysis effect in its set_false_path reference.

Documentation corrections

F5. Clarify names, bit order, and the evidence behind claims

Codex says M6 is active high “despite OEN’s name.” OEN can simply mean output enable; the name alone does not imply active low. State the observed/verified polarity without that interpretation.

Claude’s transmitter header describes 10'b1111100000 as five high bits followed by five low bits. The serializer sends the least significant bit first, so the transmitted sequence is five low followed by five high. The implemented constant is correct; the prose order is misleading.

Claude’s latest commit explicitly retracts an earlier claim that it had consulted the ALINX manual and attributes the polarity correction to display behavior and comparison. That is a useful evidence correction. The Codex README’s manual link did not return usable PDF content through the web reader during this review; its schematic/page attribution was therefore not independently revalidated here.

Codex: ax7035b_hdmi.sv:74 · Claude: hdmi_tx.sv:25 · Claude’s correction and validation statement.

Pros and cons

Codex advantages

  • Preserves the board’s original 50 MHz lab rate and gives two processing cycles per pixel.
  • Separate reset-release synchronizers match its two logic clock domains.
  • Explicitly samples RGB and control signals together; passes the one-register lab test.
  • Defines idle coordinates and differential outputs deterministically.
  • Ships a full-frame signal-decoding testbench, run instructions, pin table, limitations, and validation notes.
  • The lane helper avoids duplicating serializer wiring for clock and data.

Codex disadvantages

  • More registers and clock resources in the same-lab build; related clock crossings require timing review.
  • The two-register RGB test fails; existing unit coverage does not establish all-lab compatibility.
  • Fixed mode and implicit coupling to dvi_config.svh limit reuse.
  • Clock, timing generation and transmit logic are tightly joined in one board-specific module.
  • Lacks Claude’s local default_nettype none guards and needs the OEN wording correction.

Claude advantages

  • One 25 MHz domain for graphics and lab logic simplifies reasoning about their interface.
  • Fewer LUTs, registers and clock buffers in the matched color-stripes build.
  • Separate clock helper and transmitter make reuse on other Xilinx 7-series boards easier.
  • Detailed primitive connections and local default_nettype none reduce accidental implicit nets.
  • Propagates the actual lab clock through lab_mhz; it does not falsely tell the lab it still runs at 50 MHz.
  • The latest commit documents and corrects earlier unsupported provenance and polarity claims.

Claude disadvantages

  • Halves lab throughput whenever graphics is enabled; hard-coded cycle counts change real-time behavior.
  • Fails even the one-register RGB test because control/data alignment lacks latency compensation.
  • Leaves coordinates floating without graphics.
  • No dedicated checked-in board testbench or user README in the reviewed version.
  • Clock parameters lack legality checks; nondefault screen and color parameters are not fully supported.
  • The wrapper is longer and contains more video-specific integration details.

Source size alone is not a quality score: Codex has 185 lines of HDMI helpers and a 260-line wrapper; Claude has 328 lines of helpers and a 340-line wrapper. These counts include comments and whitespace; Codex’s separate 178-line testbench and 119-line README are excluded from those implementation counts.

Checks and recommendations

  1. Fix registered-pixel alignment before calling either implementation universal. Add known-latency RGB fixtures and real game/lab tests. Verify first/last visible pixels and row transitions. Use a defined interface latency or supported per-lab setting; avoid an unconditional extra delay that breaks combinational labs.
  2. Apply the small Claude idle fix and documentation corrections. Tie x/y to zero without graphics; correct OEN interpretation and transmitted clock-bit order.
  3. Choose the lab clock as a compatibility policy. Keep 50 MHz as the default for this existing board. An optional 25 MHz mode is reasonable after checking cycle-counted timers, UARTs, CPU workloads and graphics pipelines. Preserve accurate clk_mhz propagation.
  4. Keep the current vendor XDC plus reset exception. The matched builds confirm the intended pins. Treat any future reset-scope change separately and review non-graphics reset release. Do not restore redundant negative-pin assignments merely to make the diff larger.
  5. Add supported-parameter checks and share the verification entry point. Reject unsupported clock/resolution/color combinations. Maintain fast line-level tests for iteration and full-frame tests for vertical timing and regression. Extend the receiver model to check legal TMDS encoding and running disparity, not just decoded RGB.
  6. Test clock loss and repeated resets. The code ORs reset with loss of lock, but the fresh tests exercise the button reset. Check lock loss, startup, brief reset pulses and repeated relock using suitable models and on the board.
  7. Validate real displays and external timing. Try more than one monitor/cable, cold boot, reconnect, and reset during video. Check M6 power enable and TMDS integrity. Record which build and display were used. Resolve the external timing assumptions before claiming end-to-end timing closure.

Historical hardware evidence is separate: Claude’s commit descriptions report that the corrected design produced a picture and an older build was programmed. This review did not independently observe that. AMD’s OSERDESE2 reference documents master/slave expansion for ten-bit data, D1-first serialization, the CLK/CLKDIV relationship, and reset timing requirements. Both implementations use those primitive arrangements; fresh simulation checks the resulting bit stream at the defaults.

The MMCME2_BASE reference defines the attributes and legal settings to validate when exposing clock parameters. The set_false_path reference explains why that command changes timing analysis rather than adding reset circuitry.

The board-specific ALINX manual URL cited in the existing Codex README is AX7035B_UG.pdf. Its content was not retrievable through the web reader in this review, so it is listed as a reference to verify, not as newly checked schematic evidence.
